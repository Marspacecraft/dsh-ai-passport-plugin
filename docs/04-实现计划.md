## M3 生命周期模型（t43 起，改动此模块前必读）

`src/link/link.js` 不再是「每个方法各自改状态 + 世代号仲裁」，而是**电平触发（level-triggered）**：

- `start()` / `stop()` / `restartScan()` 只写 `#desired = { mode, reason, ... }`，**在调用瞬间落定**，然后 `return #kick()`。方法体里不应出现 `await`（这是可机械检查的约束）。
- 单一 worker `#reconcile()` 循环：重读 `#desired` → `#plan(intent)`（纯函数，返回下一小步或 `null`=已收敛）→ `#runStep()` 执行一小步 → 意图变了就丢步重规划。`#runStep` 内部**每个 await 之后**都比较 `this.#desired !== intent`，不等即返回且**不再施加任何副作用**。
- `#setState(...)` / `emit('disconnected')` / 建拆 pipeline **只能出现在 worker 的步骤里**。没有第二个施加点，就没有「陈旧效果覆盖新状态」这个缺陷面。
- 判死 / 意外断链**不自己写状态**：只发布 `connected` 意图 + 退避，路径与「用户点连接」共用。
- 用户动作在 `#publish()` 里立即 `#clearReconnectTimer()`；只有退避自己发出的意图（`reconnect: true`）才允许等 timer。**漏掉这一条会让用户点连接被静默延后到退避到期**（t44 的回归）。

为什么改模型：世代号能表达「我过期了」，表达不了「用户最后想要什么」。旧写法里 `start()` 先 `await #stopPromise` 再自增世代，await 一进，顺序就乱。

**测试纪律（血泪）**：这个模块的缺陷全在**过程中**（瞬时双管线、被覆盖的中间态），只在全部 Promise settle 之后断言一次**抓不到**——t38 实测「31 种交织」用例对四类变异全绿。不变量必须**每推进一轮就断言一次**。

## Task 1 · `ble/transport.js` 抽象基类与错误分类

**目标**：给出所有传输实现的共同抽象，以及「错误类别」与「错误文案」分离的统一出口。

**输出物**：`src/ble/transport.js`、`test/ble/transport.test.js`

**必须导出**

```js
export const LINK_STATE = {
  IDLE: 'idle', SCANNING: 'scanning', CONNECTING: 'connecting',
  CONNECTED: 'connected', RECONNECTING: 'reconnecting', FAILED: 'failed',
};
export const TRANSPORT_ERROR = {
  NOT_AVAILABLE, PERMISSION_DENIED, ADAPTER_OFF, ADAPTER_UNAUTHORIZED,
  DEVICE_NOT_FOUND, CONNECT_FAILED, DISCONNECTED, TIMEOUT, UNKNOWN,   // 值为同名小写短横线字符串
};
export class TransportError extends Error { /* (code, message, { cause, hint } = {}) */ }
export function classifyError(error)   // 任意错误 → TransportError，只定类别
export function humanizeError(error)   // 低层原文 → 人读文案，原文留在 cause
export function toUserError(error)     // = humanizeError(classifyError(error))
export class Transport extends EventEmitter {
  get state(); get mtuPayload();
  async start(); async stop(reason); async restartScan(reason);
  async send(bytes, { channel = 'control' } = {});
  // 子类钩子（下划线命名，不是 #private）：
  doStartScan(); doStopScan(); doConnect(); doDisconnect(); doSend(bytes, opts); doDispose();
  emitUnexpectedDisconnect(reason, error);
}
```

**关键约定（来自 docs/02 §4.2 与 §10，都是 v1 踩过的坑，不得"优化"掉）**

- 钩子命名为 `doStartScan / doStopScan / doConnect / doDisconnect / doSend / doDispose`，**刻意不用 `#private`**。理由：`#` 方法词法绑定，子类同名方法不会覆盖基类，钩子会静默失效。
- 基类构造函数里装一个**兜底 `error` 监听**（`if (this.listenerCount('error') > 1) return; this.lastUnobservedError = error`）。理由：EventEmitter 在无监听者时 emit('error') 会抛到调用栈，把宿主带崩。
- `classifyError` 对「已是 `TransportError` 且 `code !== UNKNOWN`」的输入**原样返回**（短路）。理由：否则上层构造的中文错误会被 message 关键字改写。
- `classifyError` 只能靠 message 关键字兜底分类（noble 不给错误码）：`permission|eperm` → PERMISSION_DENIED；`poweredoff|powered off|adapter off` → ADAPTER_OFF；`unauthoriz` → ADAPTER_UNAUTHORIZED；`cannot find module|err_dlopen_failed|different node\.js version|invalid elf header` → NOT_AVAILABLE；`not found|cannot find device` → DEVICE_NOT_FOUND；`timeout|timed out` → TIMEOUT；`disconnect|not connected` → DISCONNECTED；其它 UNKNOWN。
- `humanizeError` 只在命中**低层原文特征**时才换文案，改写后 `cause` 保留原错误。至少覆盖：`could not start scanning`、`state is powered off`、`peripheral already connected`、`cannot find package`、`Operation was aborted`。
- `#setState` 相同状态短路（不重复 emit）。
- `emitUnexpectedDisconnect` 置 `FAILED` 并 emit `disconnected` 带 `{ unexpected: true, reason, error }`。
- `send()` 在未连接时抛 `TransportError(DISCONNECTED, …)`，不做静默丢弃。

**测试必须覆盖**：状态流转与同值短路、兜底 error 监听捕获未观测错误、`classifyError` 对每个关键字分类、TransportError 短路不被改写、`humanizeError` 改写且保留 cause、`toUserError` 串联、基类钩子抛 NOT_AVAILABLE、`emitUnexpectedDisconnect` 的 payload。

**验收命令**：`node --test test/ble/transport.test.js` 全绿；并且 `node --test "test/**/*.test.js"` 中 M1 的 111 条仍然全绿。

**禁止**：在 `transport.js` 里 import 任何 `src/wire/` 之外的同层模块；引入 `noble`；实现任何真实的 BLE 调用。

## Task 2 · `ble/bridge-client.js` + `ble/bridge-worker.js` 父子进程 JSONL

**目标**：把原生 BLE 关进子进程，父进程只通过 stdin/stdout 的 JSON Lines 说命令。让「发一串字节 / 收一串字节」在父进程侧变成普通 Promise。

**输出物**：`src/ble/bridge-client.js`、`src/ble/bridge-worker.js`、`test/ble/bridge-client.test.js`

**JSONL 协议（docs/02 §4.2，不得改动形状）**

```
父 → 子   {"id":<int>,"cmd":<string>, ...args}
子 → 父   {"id":<int>,"ok":true,"value":<any>}
          {"id":<int>,"ok":false,"error":{"code":<string>,"message":<string>}}
          {"event":<string>, ...payload}        // 无 id，单向下行
```

命令集（父子两侧必须严格一致）：`init`、`scan`、`stopScan`、`connect`、`disconnect`、`write`、`readCtrl`、`dispose`、`ping`。
事件集：`ready`、`state`、`device`、`connected`、`disconnected`、`data`、`fatal`。

**父进程侧 `bridge-client.js` 必须做到**

- `class BridgeClient extends Transport`，`spawn(process.execPath, [workerPath, ...args])`；`--mock` 时子进程内部走内存设备（供 M2 集成测试用）。
- 以子进程主动发出的第一条 `{"event":"ready"}` 作为**唯一同步点**；等不到就 15 秒超时抛 `NOT_AVAILABLE`。理由：抢先写命令会石沉大海。
- 每个命令独立定时器（默认 20 秒），`unref()`；`connect` 单独用 70 秒（≥ worker 内 30 秒扫描 + 30 秒连接 + 服务发现）。
- stdout 用 `readline` 逐行解析；stderr 逐行转 `debug` 日志（不进协议）。
- `data` 事件的字节用 base64 传输，父进程解成 `Buffer` 再 emit。
- 记录 `rssiById`：noble 只在扫描发现时给 rssi，连接回包里没有，不记就永远显示 "—"。
- `disconnected` 只有 `state === 'connected'` 且非主动 `stop()` 时才当作**意外**（否则主动断开会被显示成"链路故障"）。
- 子进程退出 → 指数退避重启（`[500,1000,2000,5000,10000]`），并 emit `state` 变化；`dispose` 后不再重启。
- `stop()` / `dispose()` 里的 `sleep(ms)` **不得 unref**（await 一个 unref 定时器在事件循环空闲时永不 settle，会造成 dispose 卡死——v1 踩过，11 条用例变 cancelled）。

**子进程侧 `bridge-worker.js` 必须做到**

- 独立进程，只依赖 `node:readline` 与（懒加载的）noble。**它不知道自己服务的是 AI Passport**，只认「这个 UUID 特征要 write，那个要 subscribe」。
- `loadNoble()` 依次尝试 `@stoprocent/noble`、`@abandonware/noble`、`noble`，要求导出里有 `startScanning`；全失败则 emit `fatal` 后退出。**必须 try/catch 包住**，因为本仓库不把它列为依赖。
- 设备识别**三选一**（任一命中即认，因为广播实际 39 字节装不下 31 字节预算）：服务 UUID 命中 / 名字 ∈ `ADV_DEVICE_NAMES` / manufacturerData 前 4 字节为 `ADV_MFG_TAG`。
- 自己维护 `seen` Map（macOS 上 `noble._peripherals` 恒为空）。
- 特征发现**必须 `discoverAllServicesAndCharacteristics`，禁止传 UUID 过滤**（`@stoprocent/noble` 在 macOS 上传 UUID 过滤会静默失败，连 message 都没有）。
- `data` 监听器必须在 `subscribe()` **之前**挂上。
- MTU：`requestMtu(MTU_TARGET)` → 成功取返回，失败回 `MTU_FALLBACK`；写用 `write(bytes, true, cb)`（withoutResponse）。
- 收到主机的 `stopScan`/`disconnect` 要能中断进行中的等待；`startScan` 失败必须回滚内部 `scanning = false`，否则后续所有 scan 被永久吞掉。
- `rl.on('close')` → dispose 后 `exit(0)`；`uncaughtException` → emit `fatal` → 50ms 后 `exit(1)`。

**测试必须覆盖**（不接真机，用 `--mock` 子进程或注入假 spawn）：ready 同步点、命令超时、并发命令按 id 配对、事件透传、base64 字节还原、意外断链 vs 主动断开、子进程崩溃后重启退避、dispose 后不重启、stderr 不进协议。

**验收命令**：`node --test test/ble/bridge-client.test.js` 全绿 + 全量测试全绿。

**禁止**：把 `@stoprocent/noble` 写进 `package.json` 的 `dependencies`；在父进程里直接 `import` noble；改动 JSONL 字段名。

## Task 10 · `link/frame-io.js` 收发管线

**目标**：把 `Transport` 的字节流与 `wire/` 的分片模块粘成"能发一条消息 / 能收一条消息"
的最小可用管线，**不掺业务语义**（不识别 `type`，不做握手）。

**inScope**：`src/link/frame-io.js`、`test/link/frame-io.test.js`

**接口**：

```js
class FrameIO extends EventEmitter {
  constructor({ transport, chunkPayload, maxMessageBytes, logger })
  async sendMessage(type, payload, { ack = true, channel = 0 } = {})
  async sendRaw(channel, bytes)            // 音频用：不分配消息号、不登记 ACK
  get stats()                              // {messagesIn, messagesOut, bytesIn, bytesOut, gaps, stale, ackTimeouts}
  dispose()
}
```

**验收项**：

1. `sendMessage` 内部走 `encodeFrames` → `SendQueue` 串行发送，`ack:true` 时用
   `PendingAcks.track()` 登记；`ack:false` 时发完立即 `msgIds.release()`。
2. 收到完整消息时 `emit('message', {type, payload, msgId, channel})`；
   `type` 不是字符串时**不 emit**，记 `stats.badPayload` 并回 `nack{reason:"BAD_PAYLOAD"}`。
3. `AUDIO` 通道（channel 1）的字节**不进 `Reassembler`**，直接
   `emit('audio', {bytes, msgId, frag})`。这是 C6 的结构性保证——`wire/reassembler.js`
   里已有 `AUDIO 通道不得进入重组器` 的抛错兜底，本层必须在它之前分流。
4. 重组 `gap` 时 `emit('gap', {msgId, missing})` 并发 `nack{msgId, reason:"REASSEMBLY_GAP", missing}`。
   **只整条重发，不做部分重传**（docs/03 §2.5：部分重发没有 FIRST 会被判 stale）。
5. 收到 `ack` → `acks.acknowledge(msgId)` + `msgIds.release(msgId)`；
   收到 `nack` → 从 FIRST 起整条重发（`acks.negativeAcknowledge` 的 missing 参数**只作诊断**）。
6. `ack` 超时放弃时 `emit('ack-timeout', {msgId})` 并释放消息号。
7. 发送队列在断链时 `reject` 全部待发项，`emit` 出可观测事件，**不留悬挂 Promise**。
8. `maxMessageBytes` 超限时抛 `WireError(PAYLOAD_TOO_LARGE)`，**不静默截断**。

**验收命令**：`node --test test/link/frame-io.test.js`

**不允许**：在本层识别任何 `type` 字符串；不允许改 `src/wire/`。

## Task 11 · `link/handshake.js` 握手与配对

**目标**：实现 docs/03 §3.1–§3.5 的握手状态机，含握手前白名单与配对流程。

**inScope**：`src/link/handshake.js`、`test/link/handshake.test.js`

**行为契约**：

```
idle →(收到 hello)→ acking →(发出 hello.ack{accepted:true})→ ready
                              →(accepted:false)→ rejected（不重连，等用户干预）
```

1. **设备发起握手**：主机**不主动发 hello**，只等。这是 v2 定案，与 v1 注释相反。
2. `hello.proto !== PROTOCOL_VERSION` → 回 `hello.ack{accepted:false, code:"PROTO_MISMATCH"}`，
   随后 `emit('rejected', {code})`。**不要静默按低版本运行**（v1 只打 warn 没有降级分支）。
3. 最终值 = `min(设备 maxPayload, MAX_CHUNKS × chunkPayload, MAX_MESSAGE_BYTES_CEILING)`，
   回在 `hello.ack.maxPayload`，同时 `emit('ready', info)` 带
   `{deviceId, name, firmware, maxPayload, maxChunks, capabilities, paired}`。
4. **握手前白名单**：`pair.*` / `ping` / `pong` / `ack` / `nack` / `hello` 在 ready 之前
   也必须处理；其余业务消息**静默丢弃**（不回 nack，不 emit）。
5. **配对独立于握手**：`pair.*` 与握手是两条时间线，顺序不限。设备可以在 `hello`
   之前发 `pair.required`（docs/03 §3.1 的"明确规则"）。
6. `token` 校验：`hello.token` 与信任表匹配 → `paired:true`；不匹配 → `paired:false`
   并 `emit('pair-required', {reason:'token-mismatch'})`。
7. **环检测**：token 不匹配时**只自动重置一次**。第二次仍不匹配就停，不再重置
   （否则 `pair.required → 重置 → 旧 token 再 hello` 无限循环）。
8. 信任表读写走可注入的 `{load, save}`，默认实现写 `~/.dsh/dsh-ai-passport.pairing.json`
   且权限 `0600`。**测试不得触碰真实 home 目录**——用注入的假实现。
9. `pair.ok` 后 `emit('paired', {deviceId, token})` 并落表；`dispose()` 时不删信任表。

**验收命令**：`node --test test/link/handshake.test.js`

## Task 12 · `link/keepalive.js` 双向保活与判死

**目标**：实现 docs/03 §9.1，**这是 v1 三个缺陷的集中修复点**。

**inScope**：`src/link/keepalive.js`、`test/link/keepalive.test.js`

**行为契约**：

1. `lastInboundAt` 在**收到任意通道任意帧**时刷新——不只是 `pong`。
   本模块对外暴露 `touch(now)`，由 `link.js` 在每次入站帧时调用。
2. 每 5 秒 tick 一次：`now - lastInboundAt >= 5000` → 发 `ping`；
   `>= 30000` → `emit('dead', {reason:'keepalive-timeout'})` 并停止 tick。
   用 `>=` 而非 `>`：tick 步进恰为 5000ms，检查时刻永远精确落在阈值上，
   严格 `>` 会把首个 ping 推迟整整一个周期（空闲 10 秒才发）、判死推迟到 35 秒。
3. **有业务流量时不发 ping**（`touch` 已经刷新了 `lastInboundAt`，自然满足）。
4. **发 ping 之前不得自增任何计数**——v1 的 `missedHeartbeats += 1` 在 ping 之前，
   导致"跳过发送也计数"。v2 用时间戳比较，**没有计数器**。
5. `ping` 载荷 `{type:'ping', seq:N}`，`seq` 单调递增仅作调试；收到 `ping` 立即回
   `pong{seq}`，**收到 `pong` 不做校验**（不匹配也正常）。
6. 定时器必须可注入（`{now, setTimer, clearTimer}`），**测试用假时钟驱动，
   不许依赖真实 5 秒/30 秒等待**。
7. `stop()` 幂等，停掉 tick 后不再 emit。

**必须通过的回归（对应 docs/02 §8 的 T1）**：

> 对端只回 `ack` 不回 `pong` 时，60 秒内**不得**判死。
> 理由：`ack` 也是入站帧，证明对端活着。v1 只有 `pong` 清零，这个用例必然失败。

**验收命令**：`node --test test/link/keepalive.test.js`

## Task 13 · `link/link.js` 装配与断链清理

**目标**：把 frame-io / handshake / keepalive 装配成 docs/02 §4.3 的 `Link` 门面，

**inScope**：`src/link/link.js`、`src/link/index.js`、`test/link/link.test.js`

7. **T9 回归**：断链后 `msgIds.releaseAll()` 使全部号可复用——新连接能立刻分配

## M4 · `api/` 能力层 + `host/` 最小版

**完成标志**（docs/02 §11）：状态推送、审批、提问在 mock 下端到端跑通。

**这一层的难点不是接口，是语义**。M3 已经证明过一次：接口全对、346 条测试全绿，
仍然藏着三个「双发」「判死后假死」这类语义缺陷。M4 的语义陷阱更多，因为它是
**双端竞速**：审批和提问都同时呈现在电脑与设备上，谁先答谁赢。

四条**必须写成验收项**的语义（都来自 v1 真实事故）：

1. **电脑分支无条件启动**。v1 曾在「设备在线」时不启动电脑分支，导致设备不在

3. **`attention` 跃迁绕过节流**。500ms 节流对「状态显示」无感，对「弹提醒」有感。
4. **`session.result` 不受节流**。它是一次性事件，被合并掉就等于用户永远看不到
   结果（协议 §5.7 明确不重发）。

## Task 20 · `api/server.js` 分发表 + `api/push.js` 状态推送

**目标**：把链路收到的消息按 `type` 派发到各能力，并实现 `session.state` 的全量

## Task 22 · `host/approvals.js` 审批双端竞速

**目标**：拦截 `approval/request`，双端同时呈现，先答者胜，落败方收 done。
**这一层是 v1 事故最集中的地方，5 条约束每条都对应一次真实故障。**

**inScope**：`src/host/approvals.js`、`test/host/approvals.test.js`

**验收项**：

1. **电脑分支无条件启动**。不论设备是否在线、是否配对、工具是否在作用域内，
   电脑卡片分支都必须启动。v1 事故：设备在线时不启动电脑分支 → 设备不在身边时
   审批永久悬挂 → DSH 那轮对话卡死。
2. `deviceEligible` 判定**只决定要不要通知设备**，不影响电脑分支：
   `link.ready` && `paired` && 工具在 `approval.deviceToolScope` 范围内。
3. `deviceToolScope` 是**三值枚举** `"all"`（默认）/ `"write-only"` / `"none"`，
   **不是布尔**。布尔表达不了「只通知写操作」这个最可能被用到的中间态。
4. `Promise.race([电脑, 设备])`，`#settle()` **必须幂等**：`if (entry.settled)
   return false`。迟到裁决忽略，不报错、不改结果。
5. **落败方必须收到 `approval.done`**：设备先答 → `approval.done{decidedBy:'device'}`
   让电脑卡片收起并 abort 电脑分支；电脑先答 → `approval.done{decidedBy:'pc'}`
   让设备收起。
6. 断链 → 结算 `cancelled`（C5），`decidedBy:'disconnect'`，**电脑分支继续有效**，
   用户仍可在电脑上完成。
7. `risk` 由工具是否只读算出（只读 `low`，其余 `high`），与 `deviceToolScope`
   **无关**——作用域决定「发不发」，`risk` 只描述「发了之后告诉设备什么」。
8. 设备若提供「总是允许」，主机只能落到 `allowed-once` 并记一条 warn，
   **不为它造假的持久授权**（DSH 的 grants 只作用于本次请求）。
9. `timeoutMs` 只是**展示建议**，主机**不设审批超时**。v1 把它当成审批超时，
   `0` 被解释为「永不超时」，又叠加「设备在线即抑制电脑卡片」，导致永久悬挂。
