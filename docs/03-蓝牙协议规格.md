# AI Passport 蓝牙协议规格（v2 / 重写版）

> 状态：**草案，待用户审定**。
> 定位：本仓库（DSH 插件）是**协议服务端**，设备是**协议客户端**。
> 插件只提供能力（推送 / 拉取 / ASR / 控制），不定义设备如何显示、如何组合。
> 协议可完全重定义，**不兼容旧固件**；改动即要求设备重烧。
>
> 本文件与实现的关系：
> - 人类可读的完整规格 = 本文件
> - 机器可读的单一事实源 = `src/wire/constants.js`（见 02 设计文档 §7）
> - 一致性测试只校验「事实源 ↔ 本仓库实现」，不再跨仓库正则读 C 头文件

## 0. 本协议不做什么（边界）

这一节是需求对齐的直接产物，写在这里防止实现阶段膨胀。

| 不做 | 理由 |
|---|---|
| 不定义设备如何显示、显示几个会话、如何翻页 | 属于固件端 |
| 不做 AI 偏离预警 | 用户自己看思考过程判断 |
| 不做工具执行结果 | 用户裁决：AI 思考过程里会有展现 |
| 不做 AI 回复**全文** | 只推本轮最终回复的**前 `maxMessageBytes` 字节**（§5.7），长回复截断并置 `truncated=1`，全文去电脑看 |
| 不做实时流式思考过程 | 按需拉取即可，节省攒批与背压逻辑 |
| 不做时间线持久化 | 内存环形缓冲，会话结束即丢，重启不恢复 |
| 不做结果持久化 | `session.result` 纯推送，不落盘、不补发 |
| 不做多设备 | 当前只支持一台，协议留字段但不使用 |
| 不做链路加密 | 应用层配对是「认领/信任」，非抗窃听认证 |

## 1. 传输层

### 1.1 角色

| 层次 | 谁主动 |
|---|---|
| BLE 传输 | 主机（Mac）为 central，扫描并连接设备 |
| 协议会话 | **设备**为客户端，连接后由设备发 `hello` 发起握手 |

这两件事方向相反但不矛盾：BLE 连接由主机发起，协议握手由设备发起。

### 1.2 广播

设备广播内容（31 字节预算，BLE 4.0 legacy advertising）：

| 字段 | 长度 | 内容 |
|---|---|---|
| Flags | 3 | `0x02 0x01 0x06` |
| 128 位服务 UUID | 18 | 见 1.3 |
| Manufacturer Specific Data | ≥ 4 | 前 4 字节 ASCII `FAP1`（`AP_ADV_MFG_TAG`） |

**识别策略（三选一，任一命中即认）**，因为 31 字节放不下 UUID + 名字 + 厂商数据：

1. 广播或扫描响应含服务 UUID
2. 本地名 ∈ `{FoloPassport-DSH, Folo-PSP, FoloPassport}`
3. 厂商数据前 4 字节 === `FAP1`

命中后仍必须做 GATT 服务发现校验，不匹配则判为系统 BLE 缓存残留（`stale-cache`）而非冒牌设备。

> 旧实现踩过的坑：曾按 UUID 推导（三版全错）、曾把 `0x02` 当 TX 特征（导致"能连上但握手超时"）、曾在 macOS 上用 UUID 过滤调用 `discoverSomeServicesAndCharacteristics`（静默失败且 err 无 message）。新实现一律**全量发现 + JS 侧匹配**。

### 1.3 GATT 特征

服务 UUID：`0000a900-a900-5041-5353-544f524f5350`

| 特征 | UUID 后缀 | 属性 | 方向 | 用途 |
|---|---|---|---|---|
| RX | `…f0a90002` | Write Without Response | 主机 → 设备 | 控制帧 + ASR 音频 |
| TX | `…f0a90003` | Notify | 设备 → 主机 | 全部上行帧 |
| AUDIO | `…f0a90004` | Notify | 设备 → 主机 | 设备录音上行 |
| CTRL | `…f0a90005` | Read | 主机读取 | 静态信息（能力/固件/电量） |

#### 1.3.1 这套 UUID 是刻意构造的

**不是笔误，不要"修正"成标准 base UUID。** 服务的后 24 位 hex 与特征的
前 24 位 hex 逐字节相同，构成重叠拼接：

```
SERVICE_UUID : 0000a900 a90050415353544f524f5350
CHAR_*_UUID  :          a90050415353544f524f5350 f0a9000N
                         └────── 相同的 24 hex ──────┘
```

中段 10 字节 `a9 00 50 41 53 53 54 4f 52 4f 53 50` 按 latin1 解码为
`"PASSTOROSP"`；特征末尾 4 字节 `f0a9000N` 是区分码（`N` = 2/3/4/5）。

改成标准 Bluetooth SIG base UUID 属于协议变更，需要双端同步重烧且收益为零，
因此保持现状。改动这里的 hex 等于改动协议本身。

> 文档写法提醒：UUID 一律写成标准 5 段 `8-4-4-4-12`。曾出现过正文用 `8-4-4-4-4-8`
> 分段、与附录 B 不一致的情况——去掉连字符后是同一串 32 hex，但分段错误无法被
> 「附录 B ↔ constants.js」的一致性测试发现。

> **AUDIO 特征只用于设备 → 主机。** 协议不定义主机 → 设备的音频下行，因此 `sendVoice` 这类能力在 v2 中不存在。

CTRL 特征读取格式（16 字节，二进制）：

| 偏移 | 长度 | 内容 |
|---|---|---|
| 0 | 2 | 协议版本（LE uint16） |
| 2 | 2 | 能力位掩码（LE uint16） |
| 4 | 2 | 单条消息最大载荷（LE uint16） |
| 6 | 2 | 固件版本主次（各 1 字节） |
| 8 | 1 | 电量百分比（0..100，255 = 未知） |
| 9 | 7 | 保留，填 0 |

> CTRL 只作为**连接早期的快速探测**（无需等握手）。握手后的权威值以 `hello` 为准（设备可在运行中刷新电量）。

### 1.4 MTU 与分片尺寸

- 主机请求 MTU 517（BLE 4.2 ATT 上限）
- 协商失败时兜底到 **247**（固件 `preferred MTU ≥ 247`）。247 而非 244 是刻意的：
  244 相减后不是整数倍的常用值，而 247 − 3 − 4 = **240** 是固件缓冲按 240 对齐的取值
- 有效分片载荷（**权威公式**）：

  ```
  attPayload   = max(20, mtu - 3)     # 减去 ATT 操作码 1 字节 + 句柄 2 字节
  chunkPayload = attPayload - 4        # 减去 4 字节协议帧头
  ```

- 各 MTU 下的确切值（**实现必须用这张表，不要自己推**）：

| 协商 MTU | `attPayload` | `chunkPayload` | `16 × chunkPayload` |
|---|---|---|---|
| 517（目标） | 514 | **510** | 8160 |
| 247（兜底） | 244 | **240** | 3840 |
| 244（部分安卓/旧驱动） | 241 | **237** | 3792 |
| 23（BLE 规范最小值） | 20 | **16** | 256 |

- 注意 244 与 247 只差 3，但片载荷差 3 字节（237 vs 240）。**MTU 不能假设**，
  必须每次连接后按实际协商值重算 `chunkPayload`，并在 `hello.ack` 里告知设备

**单条消息上限**：`maxMessageBytes = min(设备声明 maxPayload, 16 × chunkPayload, 8160)`

- 16 = `MAX_CHUNKS`（4 位分片号上限）
- 8160 = 16 × 510（MTU 517 时的理论上限）
- 该值在 `hello.ack` 中由主机**最终确定并告知设备**，因为只有主机知道 MTU

## 2. 帧格式

### 2.1 帧头（4 字节）

| 字节 | 位 | 字段 |
|---|---|---|
| 0 | 7..4 | `version`（当前 2） |
| 0 | 3..0 | `flags` |
| 1 | 7..0 | `channel` |
| 2 | 7..0 | `msgId` bit 11..4 |
| 3 | 7..4 | `msgId` bit 3..0 |
| 3 | 3..0 | `frag`（分片序号 0..15） |

`msgId` 12 位 → 4096 个在途消息号。`frag` 4 位 → 每条消息最多 16 片。

### 2.2 flags

| 位 | 名称 | 含义 |
|---|---|---|
| 0 | `FIRST` | 本条消息的第一片 |
| 1 | `LAST` | 本条消息的最后一片 |
| 2 | `ACK_REQ` | 本片所在消息需要接收方回 `ack` |
| 3 | 保留 | 填 0 |

单帧消息同时置 `FIRST|LAST`。空载荷也产生 1 片（`total = max(1, ceil(len / chunkPayload))`）。

### 2.3 通道

| 值 | 名称 | 内容 | 分片语义 |
|---|---|---|---|
| 0 | `CONTROL` | UTF-8 JSON | 重组为完整消息后解析 |
| 1 | `AUDIO` | 原始字节（PCM 或 ADPCM） | **不重组**，按到达顺序追加 |
| 2 | `HEARTBEAT` | 极小 JSON（`ping`/`pong`） | 单帧 |
| 3 | `LOG` | UTF-8 文本（设备日志） | 单帧，默认关闭 |

**AUDIO 通道的特殊规则（重点）**：

- 不做重组、不做去重、不按 `frag` 排序
- `frag` 只是**流序号**（4 位回绕），用于统计断档，**不参与逻辑**
- 消息边界由 `asr.begin` / `asr.end` 界定，音频帧本身不携带边界标志
- 理由：旧实现曾按 `seq` 去重，结果 30 秒录音只剩第一条 0.26 秒

### 2.4 重组规则

接收方以 `key = "{channel}:{msgId}"` 维护重组缓冲：

| 情况 | 处理 |
|---|---|
| 收到 `FIRST` | 丢弃同名残留，新建缓冲（重传的一轮才是权威内容） |
| 无 `FIRST` 就来片 | 丢弃，计入 `stale` |
| `frag` 重复 | 忽略该片 |
| `frag ≠ 上次+1` | **丢弃整条消息**，回 `nack {msgId, reason:"gap", missing:[…]}` |
| 累积字节数超上限 | 丢弃整条，回 `nack {msgId, reason:"overflow"}` |
| 同时满足「见过 LAST」+「0..lastFrag 连续」+「字节数与声明一致」 | 完成，交上层 |

### 2.5 确认与重传

- 只有 `CONTROL` 通道的消息可要求 ACK（`ACK_REQ`）
- 每条消息的**所有分片**都带 `ACK_REQ`（丢中间片时接收方立刻察觉）
- 接收方整条重组成功后回 `ack {msgId}`
- 发送方超时未收到 `ack` → 重传；超时序列 **400 / 800 / 1600 ms**（指数退避），共 3 次
- 3 次仍失败 → 释放消息号，向上层报 `ACK_TIMEOUT`

**`nack` 的 `missing` 只是诊断信息，不是重传指令。**

这一点必须写清楚，因为 §2.4 的「gap 即丢弃整条」与「只重发缺失片」在逻辑上
不能同时成立：接收方一旦发现缺口就把整条缓冲删了，此时即使发送方只补发
缺失片，后到的片没有 `FIRST`，按 §2.4 只能判为 `stale` 再次丢弃——
**选择性重传永远无法完成重组**。

实测（M2 验收时用 `Reassembler` 直接验证）：

```
frag0 → pending
frag1 → pending
frag3 → gap missing=[2]      ← 缓冲已删
frag2（只补缺失片）→ stale    ← 补了也没用
frag4 → stale
```

因此 v2 的规则是：

| 触发 | 发送方动作 |
|---|---|
| 收到 `nack{gap, missing:[…]}` | **从 `FIRST` 起整条重发**（唯一能成功的路径） |
| 收到 `nack{overflow}` | 整条重发；若再次溢出，放弃并报 `ACK_TIMEOUT` |
| ACK 超时 | 整条重发，最多 3 次 |

`missing` 保留在协议里，用途是**观测与诊断**：设备可以据此统计丢片率、
定位劣化的 MTU 档位。发送方收到 `nack` 时应当开始整条重传，**不必**先核对
`missing` 再决定发哪些片。

> 为什么不在 v2 改成「gap 时保留缓冲、真正支持选择性重传」：那需要接收方
> 为每条在途消息保留最多 8KB 缓冲并维护位图，而设备端没有 PSRAM（C9 约束）。
> 整条重发的代价是「一次丢片多发几片」：按 §1.4 的 `maxMessageBytes = min(设备声明
> maxPayload, 16 × chunkPayload, 8160)`，最坏情形（MTU 517、满 8160 字节消息）
> 一次丢片要重发 16 片，典型情形（MTU 247、2KB 左右的消息）重发 9 片；
> 保留缓冲的代价是内存不可控。这是权衡后的选择，不是遗漏。
>
> `src/wire/acks.js` 里保留 `selective` 统计字段与 `negativeAcknowledge(msgId, missing)`
> 接口，供未来真要做选择性重传时复用；**当前 `link` 层不要用它做「只发缺失片」**。

### 2.6 消息号分配

- 12 位环形分配，跳过在途号
- 耗尽（4096 个全在途）→ 抛错并上报 `MSGID_EXHAUSTED`
- **所有释放路径必须闭合**：正常 ack、nack 放弃、发送失败、超时放弃
- 旧实现的泄漏点：gap 时不释放，要等 3 次 ACK 超时（约 2.8 秒）才回收

## 3. 会话建立

### 3.1 握手

```
设备                                  主机
 |  (BLE 已连接)                        |
 |--- hello{proto,caps,maxPayload,fw,token?} -->|
 |<-- hello.ack{proto,caps,maxPayload,paired} --|
 |                                    |
 |  (双方记 handshakeComplete = true)  |
```

- 设备在 BLE 连接成功后**主动**发 `hello`
- 主机回 `hello.ack`，其中的 `maxPayload` 是最终生效值，`accepted` 表示是否继续
- 握手完成前，主机不主动下发任何**业务**消息
- 握手完成前，设备发来的**业务**消息被主机丢弃（静默，不回 `nack`）
- 主机重连后重新握手，不沿用上一次会话的任何状态

**握手前的合法例外（白名单）**：下面这些消息在握手完成**之前**也是合法的，
主机不得丢弃：

| 消息 | 为什么必须放行 |
|---|---|
| `pair.required` / `pair.ok` / `pair.failed` | 配对可能在握手完成前就开始。设备无 token 时会先发 `pair.required` 要求认领，此时还没到握手 |
| `ping` / `pong` / `ack` / `nack` | 链路层消息，与握手无关 |
| `hello` | 本身 |

> **配对时序的明确规则**：`pair.*` 与握手是**两条独立的时间线**，顺序不限。
> 常见顺序是 `hello{无token}` → `hello.ack{paired:false}` → `pair.required` →
> `pair.begin` → `pair.ok` → 设备重发 `hello{带token}` → `hello.ack{paired:true}`。
> 设备也可以在发 `hello` 之前就发 `pair.required`，主机同样要处理。

### 3.2 hello（设备 → 主机）

```json
{
  "type": "hello",
  "proto": 2,
  "caps": 63,
  "maxPayload": 8192,
  "fw": "2.0.0",
  "token": "0123456789abcdef0123456789abcdef"
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `proto` | int | 设备支持的协议版本 |
| `caps` | int | 能力位掩码（见 3.4） |
| `maxPayload` | int | 设备接收缓冲能容纳的单条消息最大字节数 |
| `fw` | string | 固件版本，仅展示 |
| `token` | string | 32 位十六进制配对令牌，未配对时省略 |

### 3.3 hello.ack（主机 → 设备）

```json
{
  "type": "hello.ack",
  "accepted": true,
  "proto": 2,
  "maxPayload": 8160,
  "maxChunks": 16,
  "server": "dsh-ai-passport/2.0.0",
  "paired": true
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `accepted` | bool | **是否接受本次握手**。`false` 时其余字段无意义，主机随后断开 |
| `code` | string? | `accepted = false` 时的原因码，见 §11 |
| `proto` | int | 协商后实际使用的版本 = min(双方)。`accepted = false` 时可为 0 |
| `maxPayload` | int | **最终生效**的单条消息上限。仅 `accepted = true` 时有意义 |
| `maxChunks` | int | 固定 16 |
| `paired` | bool | 本次握手是否已通过配对校验。仅 `accepted = true` 时有意义 |

成功示例：

```json
{ "type": "hello.ack", "accepted": true, "proto": 2, "maxPayload": 8160,
  "maxChunks": 16, "server": "dsh-ai-passport/2.0.0", "paired": true }
```

失败示例（版本不兼容）：

```json
{ "type": "hello.ack", "accepted": false, "code": "PROTO_MISMATCH",
  "server": "dsh-ai-passport/2.0.0" }
```

> **为什么需要 `accepted` / `code`**：旧设计只说"回 ack 后立即断开"，设备无法区分
> "版本不兼容，别重试"和"链路抖动，快重连"。加两个字段后设备可以据此决定：
> `PROTO_MISMATCH` → 显示"需要更新固件"并停止重连；其它 → 正常退避重连。

### 3.4 能力位

| 位 | 名称 | 置位含义 | 主机据此的行为 |
|---|---|---|---|
| 0 | `DISPLAY` | 有屏幕 | 未置位则不推送审批/提问（改为只回结果） |
| 1 | `INPUT_NAV` | 有按键/编码器 | 仅设备内部使用，主机不关心 |
| 2 | `INPUT_TOUCH` | 有触摸 | 同上 |
| 3 | `MIC` | 有麦克风 | 未置位则 ASR 请求一律拒绝（`ASR_NO_MIC`） |
| 4 | `SPEAKER` | 有扬声器 | 未置位则 `notice.sound` 忽略 |
| 5 | `BATTERY` | 有电量上报 | 未置位则 `batteryPercent` 恒 null |
| 6 | `NOTIFY` | 有提示音/背光/指示灯 | 未置位则 `notice` 只做静默记录 |
| 7..15 | 保留 | 填 0 | — |

> 旧实现的 `CAPABILITY` 常量只有 mock 在用，真实链路从不按能力位分支。v2 让它真正起作用。

### 3.5 应用层配对

不走 BLE bonding/passkey（macOS 的 noble 配对体验差，换主机要反复配对）。流程：

```
1. 设备首次连接，无 token → 设备显示 6 位一次性码，发 pair.required
2. 用户在电脑上输入码 → 主机发 pair.begin{code, host}
3. 设备校验 → 成功回 pair.ok{deviceId, token}，失败回 pair.failed{reason, remaining}
4. 主机把 {deviceId, token} 存入信任表（~/.dsh/dsh-ai-passport.pairing.json，权限 0600）
5. 之后每次 hello 带 token，主机校验通过 → hello.ack.paired = true
```

| 消息 | 方向 | 载荷 |
|---|---|---|
| `pair.required` | D→H | `{reason?: "first"|"token-mismatch"}` |
| `pair.begin` | H→D | `{code: "123456", host: "Paul-MacBook"}` |
| `pair.ok` | D→H | `{deviceId: "…", token: "…32hex…"}` |
| `pair.failed` | D→H | `{reason: "bad-code"|"rate-limited", remaining?: 3}` |
| `pair.reset` | H→D | `{ack?: true}` |

**环检测**：token 不匹配时主机**只自动重置一次**。否则 `pair.required → 重置 → 旧 token 再 hello` 会无限循环。

**安全边界（如实声明）**：配对码与 token 走**未加密**的 BLE。它的作用是"认领设备 / 决定谁可以驱动它"，不是抗窃听的认证。近距离攻击者可以嗅探到 token 并伪装成主机。

## 4. 消息总表

`D→H` = 设备到主机，`H→D` = 主机到设备。

### 4.1 通用

| type | 方向 | 用途 |
|---|---|---|
| `hello` | D→H | 握手请求（3.2） |
| `hello.ack` | H→D | 握手应答（3.3） |
| `ping` | 双向 | 保活探测 |

## 5. 推送族

### 5.1 session.state（会话集合快照）

**全量快照，不做增量 diff。** 设备自己比对要不要重绘。

```json
{
  "type": "session.state",
  "ver": 184,
  "part": 1,
  "parts": 1,
  "sessions": [
    {
      "id": "s_8f2a",
      "role": "main",
      "state": "running",
      "title": "重构蓝牙协议",
      "model": "deepseek-v4.1-flash",
      "cwd": "/Users/paul/Git/dsh-ai-passport-plugin",
      "elapsedMs": 187000,
      "attention": "none"
    },
    {
      "id": "s_31c9",
      "role": "sub",
      "parentId": "s_8f2a",
      "state": "running",
      "title": "调研 GATT 特征",
      "model": "deepseek-v4.1-flash",
      "cwd": "/Users/paul/Git/dsh-ai-passport-plugin",
      "elapsedMs": 62000,
      "attention": "none"
    }
  ]
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `ver` | int | **连接内**单调递增的版本号，从 1 开始。语义见下方「`ver` 的作用域」 |
| `part` / `parts` | int | 分片序号 / 总片数。整份快照装不下一条消息时拆成多条 |
| `sessions` | array | 会话列表，可空数组（表示当前无会话） |
| `sessions[].id` | string | 会话 ID，稳定不变 |
| `sessions[].role` | `"main"` \| `"sub"` | **必须显式给出** |
| `sessions[].parentId` | string? | `role = "sub"` 时必有 |
| `sessions[].state` | 枚举 | 见下 |
| `sessions[].title` | string | 会话标题，可为空串。主机侧**截断到 200 code point**（设备屏幕放不下更长的），截断只作用于本字段 |
| `sessions[].model` | string? | 模型名，如 `"deepseek-v4.1-flash"`。未知时省略 |
| `sessions[].cwd` | string? | 工作目录绝对路径。未知时省略 |
| `sessions[].elapsedMs` | int? | 运行时长。**起点不可靠时整个字段省略**，不是填 0 |
| `sessions[].attention` | 枚举 | `none` / `approval` / `question` |

> **`title` 为什么要限长**：`session.list` 与 `session.state` 都得保证「单个会话对象一定
> 装得进一条消息」。否则只有两条退路，都是坏消息：`session.list` 只能把该会话整条丢弃
> （设备上少一个会话，且协议里没有 `dropped` 字段能告诉它），`session.state` 只能发一个
> 超过 `maxMessageBytes` 的单片（设备可能直接拒收整个快照）。把 `title` 截到 200 之后，
> 单个会话对象的 JSON 恒在几百字节量级，这两条退路都不会被触发。`model` / `cwd` 由宿主
> 控制、本身有界，不需要额外截断。

`state` 取值：

| 值 | 含义 |
|---|---|
| `idle` | 就绪但未在跑 |
| `running` | 正在执行 |
| `waiting` | 阻塞，等待用户（审批或提问） |
| `done` | 本轮完成（保持 8 秒后转 `idle`） |
| `error` | 出错了 |

#### 5.1.1 `ver` 的作用域（**关键，实现必须遵守**）

`ver` 是**单条连接内**的单调计数器，不是全局持久化的版本号。规则：

| 时机 | 动作 |
|---|---|
| 每次握手成功（收到 `hello.ack` 且 `accepted = true`） | 主机把 `ver` 重置为 **0**；设备把本地 `lastVer` 重置为 **0** |
| 主机推出一条新快照 | `ver += 1` |
| 设备收到 `ver > lastVer` | 接受，并 `lastVer = ver` |
| 设备收到 `ver <= lastVer` | 丢弃（重复或乱序），静默忽略 |

**为什么必须重置**：`ver` 若跨连接持久化，主机重启后会从 1 重新计数，而设备还记着
上次连接末端的 `ver = 184` → 设备把所有新快照当成旧数据丢弃，表现为"连上了但屏幕
不动"，且只有等主机推 184 次才恢复。这是典型的一次性踩坑。

**为什么不用全局单调**：全局单调需要主机落盘 `ver`，而 `ver` 只是个防重放/防乱序的
序号，没有任何业务含义。连接内单调 + 握手重置既够用又无状态。

**多 part 快照的 `ver`**：同一次快照拆出的所有 part **共用同一个 `ver`**，
靠 `part`/`parts` 区分。设备按 `(ver, part)` 组装。

#### 5.1.2 通用拆分信封（**所有可能超限的消息都必须遵守**）

不是 `session.state` 独有的机制。任何一条 JSON 消息的内容可能超过 `maxPayload` 时，
统一用下面三个字段拆分 —— **字段名与语义在整份协议里只有这一套**：

| 字段 | 类型 | 说明 |
|---|---|---|
| `ver` | int | 本次逻辑消息的批次号。同一逻辑消息的所有 part **共用同一个 `ver`** |
| `part` | int | 分片序号，**从 1 开始**，最大等于 `parts` |
| `parts` | int | 总片数。不拆分时也必须显式写 `1`，**不允许省略** |

```
{ "type": "...", "ver": N, "part": i, "parts": M, ...其它业务字段... }
```

**适用范围**（当前已知会超限的）：

| 消息 | 方向 | 是否会超限 | 说明 |
|---|---|---|---|
| `session.state` | 主机 → 设备 | 会话多时会 | §5.1 |
| `session.list` | 主机 → 设备 | 同上（内容与 `session.state` 完全一致） | §6.1 |
| `timeline` | 主机 → 设备 | 20 条思考原文很容易超过 `maxPayload` | §6.2 |
| `question.asked` | 主机 → 设备 | `detail` 是计划正文时会 | §5.4 |
| `asr.result` | 主机 → 设备 | 识别文本很长时会 | §7.2 |
| `session.input` | **设备 → 主机** | `text` 很长时会 | §8.1a |
| 其它推送族 | 主机 → 设备 | 理论上会，实现时应统一走此机制 | — |

**两个方向用同一套字段**，但**组装方相反**：

| 方向 | 谁拆分 | 谁组装 | 谁发 ack |
|---|---|---|---|
| 主机 → 设备（推送/应答） | 主机 | 设备 | 无应用层 ack，失败靠链路重传 |
| 设备 → 主机（`session.input`） | 设备 | 主机 | **主机在收齐 `part = parts` 后**才回 `session.input.ack` |

**设备 → 主机的特殊规则**（只有 `session.input` 一条消息走这个方向的分片）：

1. 所有 part 共用**同一个 `reqId`**（不是 `ver` 之外再加一个 ID，`reqId` 就是配对键）
2. 主机**只有收齐 `part = 1..parts`** 才把 `text` 拼接并投递进会话
3. `session.input.ack` **只在收齐后发一次**，`reqId` 与请求一致。中间片不回 ack
   （链路层 ACK 已保证每片到达，应用层不必逐片确认）
4. **组装超时 10 秒**未收齐 → 主机丢弃半成品，**不回 ack**。设备按自己的重试策略
   整条重发（`reqId` 应换新，避免与已丢弃的半成品混淆）
5. `parts` 同样**不允许省略**，单帧也必须写 `parts = 1, part = 1`

> **为什么不给 `session.input` 加长度上限**：设备已经通过 ASR 拿到文本，
> 一段口语转写几乎不可能超过 `maxMessageBytes`（典型 3840 字节 ≈ 1280 汉字）。
> 但"几乎不可能"不等于"不可能"——用户可能粘贴或设备将来支持更长的输入。
> 与其硬性截断（会静默丢内容，违反 C1），不如让分片机制兜住。

**`ver` 的作用域**：与 §5.1.1 相同 —— 连接内单调，握手后重置。但注意它**按消息类型
独立计数**（`session.state` 的 `ver` 与 `asr.result` 的 `ver` 互不干扰），否则两条不同
消息的 `ver` 会互相"吞掉"。

**设备侧组装规则**（固件实现必须照做）：

| 情况 | 设备动作 |
|---|---|
| 收到 `part = 1` | 丢弃**同 type 同 ver** 的残留半成品，新建缓冲 |
| 收到 `part > 1` 但没有对应半成品 | 丢弃该片。**不要**指望主机重发这一片——链路层 ack 只保证「这一片字节到了」，主机不会缺 ack，见下方「链路层 ack ≠ 组装成功」 |
| 收齐 `1..parts` 全部 `part` | 按 `part` 顺序拼接业务字段，解析为完整消息 |
| 组装中途收到**更大** `ver` 的 `part = 1` | 丢弃旧半成品，开始组装新批次 |
| 组装中途收到**更小** `ver` 的任意 `part` | 丢弃该片 |
| **组装超时**：距首片超过 **10 秒**仍未收齐 | 丢弃半成品，设备可重发拉取请求 |
| 收到 `part > parts` 或 `parts = 0` 等畸形值 | 丢弃该片并记诊断日志，不影响其它组装 |
| 收到的 `part = 1` 声明的 `parts` 与缓冲中残留的不同 | 视为新批次，丢弃残留、按新 `parts` 重建 |
| `parts` 声明为 3 但收到 `part = 1,2,3,4` | 收完 3 片即视为完成，第 4 片丢弃 |

> **为什么 `parts` 不允许省略**：省略后"单帧消息"与"多帧消息的第 1 片"在语义上
> 无法区分，固件必须靠"有没有收到 part=2"来猜，而超时判定就无从下手。

#### 5.1.2.1 链路层 ack ≠ 组装成功（**固件实现必须照做**）

这是 M4 评审发现的一处协议歧义，必须在固件动工前钉死，否则「缺 ack 重发」这个
前提根本不成立。

**事实**：每个 `part` 是独立的一条链路层消息，有**各自的 `msgId`、各自的 ACK**。
主机收到第 3 片的链路层 ack，只说明「第 3 片的字节到了」，**完全不代表**设备把它
放进了组装缓冲、更不代表整条逻辑消息能拼起来。所以主机那一侧从头到尾**不会缺 ack**，
`§5.1.2` 表格里设备侧「等待发送方重传」的说法没有抓手。

**双方约定**：

| # | 约定 | 违反的后果 |
|---|---|---|
| 1 | 设备开始组装 `part = 1` 时若缓冲不足（无 PSRAM、并发批次过多），**必须对该片不回链路层 ack**，让主机 ack 超时并中止整条逻辑消息；**不得「先 ack 再丢」** | 主机以为送达、设备手里是残片，消息**静默丢失**，且在 10 秒超时后才暴露 |
| 2 | 主机任何一片 ack 超时 → **整条逻辑消息判定失败**，不得只丢该片继续发剩余片（否则设备永远拼不齐，而且每片都「成功」了） | 设备侧组装缓冲被半成品长期占用，后续批次全被挤掉 |
| 3 | 设备在 10 秒组装超时后丢弃半成品即可，**不需要也无法**通知主机（链路层没有"整条消息失败"这个信号） | — |

**由此产生的业务层要求**：一次性消息（`question.asked`、`approval.asked`）一旦发送失败
就**没有第二次机会**，主机必须自己降级，不能假设设备一定收到的：

- `approval.asked` 发送失败 → 电脑端分支本来就无条件启动（D27），用户仍能在电脑上答，不悬挂。
- `question.asked` 发送失败 → 主机**必须立即按 `cancelled` 结算该提问**并把选择权交回电脑端，
  不能挂着等一个永远不会来的 `question.answer`（否则 DSH 对话卡死，与 v1 事故同型）。

**多来源拆分的交错**：不同 `type`（或同 type 不同 `ver`）的 part 可以任意交错到达。
`session.state` 的两片中间插进 `asr.result` 的一片是合法的 —— 组装缓冲必须按
`(type, ver)` 分开维护，不能用一个全局"正在组装"槽位。

**多发状态的设计说明**：

| 问题 | 决策 |
|---|---|
| 何时推 | 任一字段变化即推（自由文本 `title` 变化也算） |
| 去重 | 主机侧只在「序列化后的内容」变化时推 |
| 频率 | **最小间隔 500ms**：内容有变化但距上次推送不足 500ms 时，合并为一次延迟推送（取最后一次状态），不排队堆积 |
| 时钟更新 | `elapsedMs` 单独变化时同样受 500ms 节流约束，设备端可自行插值走秒 |
| 拆分 | 内容超 `maxPayload` 时按 `part/parts` 拆，组装规则见 §5.1.2 |
| 为什么不推增量 | 会话数通常 <10，全量几十字节到 2KB，比分页增量简单得多 |

**为什么 `role` 必须显式**：主会话也可能有子会话；仅靠 `parentId` 是否存在来推断主从是错的。旧实现把子代理会话一并计入「N 个任务执行中」，造成虚假计数和时长基准跳变——这正是要修的缺陷。

### 5.2 approval.asked

**全文，不截断。** 设备按自己的屏幕宽度决定怎么显示、要不要分页。

```json
{
  "type": "approval.asked",
  "id": "ap_7k2n_1",
  "toolName": "write",
  "reason": "写入工作区文件",
  "displayReason": "写入工作区文件",
  "risk": "high",
  "detail": { "field": "path", "value": "src/ble/host-link.js" },
  "timeoutMs": 0,
  "callId": "call_abc123"
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | 审批 ID，用于 `approval.decide` 回填 |
| `toolName` | string | 完整工具名，不截断 |
| `reason` | string? | 原始原因文本 |
| `displayReason` | string? | 已本地化的原因（多语言对象取 `zh` → `zh-CN` → `en`） |
| `risk` | `"low"` \| `"high"` | 只读工具为 `low`，其余 `high` |
| `detail` | object? | 该工具的一个关键字段（见 5.2.1） |
| `timeoutMs` | int | 设备侧展示建议时长。0 = 一直显示到收到 `approval.done`（默认） |
| `callId` | string? | DSH 的调用 ID，仅透传 |

#### `timeoutMs` 的语义

审批的生死由 DSH 宿主决定（`req.signal` 中止、或用户裁决），主机**不额外设审批超时**。

`timeoutMs` 只是给设备的**展示建议**：

- `0`（默认）：一直显示，直到收到 `approval.done` 才收起卡片。
- `> 0`：设备可在此时间后自行收起卡片（比如为了省电或让位给别的提醒），
  但**审批本身仍然有效**——电脑端卡片一直在，用户随时可以在电脑上裁决。
  主机若在设备收起后收到设备迟到的 `approval.decide`，按正常裁决处理。

> v1 的缺陷是把 `timeoutMs` 当成了审批超时：`0` 被解释为"永不超时"，
> 又叠加"设备在线即抑制电脑卡片"，结果设备不在身边时审批永久悬挂、
> DSH 那轮对话卡死。v2 把两件事分开：**审批无主机超时，展示可以自行收起。**

### 5.3 approval.done

审批结束（设备裁决、电脑端裁决、超时、中止、断链）都发这条，让设备收掉卡片。

```json
{
  "type": "approval.done",
  "id": "ap_7k2n_1",
  "outcome": "allowed-once",
  "decidedBy": "device"
}
```

| `outcome` | 含义 |
|---|---|
| `allowed-once` | 允许（DSH 只有"一次"这一种粒度） |
| `rejected` | 拒绝 |
| `cancelled` | 被取消（工具中止 / 断链 / 应用退出） |
| `unavailable` | 无人可答 |
| `timeout` | 超时 |

`decidedBy` ∈ `device` / `pc` / `panel` / `timeout` / `abort` / `disconnect`。

> **设备端"总是允许"的语义**：DSH 的审批结果只有 `allowed-once`，`grants apply only to the requested action`。设备若提供"总是允许"按钮，主机只能落到 `allowed-once`，并记一条 warn。v2 明确不为它造假的持久授权。

### 5.4 question.asked

**全文，不截断。整批一次下发**（不再逐题下发）。

```json
{
  "type": "question.asked",
  "callId": "q_9m4x",

  "deadlineMs": 120000,

    {
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `callId` | string | 提问批次 ID，用于 `question.answer` 回填 |
| `kind` | `"choice"` \| `"plan"` | `plan` = 计划评审 |
| `deadlineMs` | int | 剩余毫秒；0 = 不超时（计划评审） |
| `questions[]` | array | 完整题目列表 |

| `questions[].question` | string | **完整题干**，不截断 |

| `questions[].multiSelect` | bool | 是否多选 |

| `questions[].options[]` | array | 完整选项，`label` 与 `description` 都不截断 |

> **`custom` 恢复为有意义的字段。** 旧设计里设备无文字输入，`custom` 恒为 0。有了 ASR，设备可以先申请 ASR 拿到文本，再填入自定义答案，所以 `custom` 照常下发。

#### 5.4.1 关于计划评审的 `detail`

计划评审的 `detail` 是整个计划正文（1–2KB，可能更大）。旧实现把它砍掉了，导致设备只能"盲批"。

v2 的处理：

- `detail` **照常下发**，不做长度限制
- 若单条 `question.asked` 超过 `maxPayload`，按 `part/parts` 拆分（同 5.1 的机制），设备按 `ver` 组装
- 设备可以边收边显示，也可以收完再显示——属于固件端决策

### 5.7 session.result（主机 → 设备）

会话**本轮完成**时推送回复结果。设备"会话完成要看到结果"的唯一推送通道。

```json
{
  "type": "session.result",
  "sessionId": "s_8f2a",
  "ver": 7, "part": 1, "parts": 1,
  "turnId": "t_3f81",
  "state": "done",
  "text": "重构完成：新增 wire 层 6 个模块，218 条单测全绿。",
  "truncated": 0,
  "elapsedMs": 412000,
  "hostEpochSec": 1762776000
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `sessionId` | string | 哪个会话完成了 |
| `ver` / `part` / `parts` | int | 拆分信封字段（§5.1.2）。**`session.result` 永远 `parts = 1`**（超限走截断而非拆分，见 §5.7.2）；`ver` 按 `session.result` 类型独立计数 |
| `turnId` | string | 本轮 ID，用于设备去重（同一 `turnId` 只处理一次） |
| `state` | `"done"` \| `"error"` \| `"aborted"` | 本轮的结局 |
| `text` | string | 助手最终回复正文。**超 `maxMessageBytes` 时截断**（不拆多 part），见 §5.7.2 |
| `truncated` | `0` \| `1` | `text` 是否被主机裁剪过。见下方"为什么" |
| `elapsedMs` | int? | 本轮耗时。起点不可靠时整个字段省略（同 §5.1） |
| `hostEpochSec` | int | 主机侧完成时刻（unix 秒），设备可用来显示"几分钟前" |

#### 5.7.1 `text` 取哪一部分

DSH 的 `assistant/message` 里内容块可能是多种类型。规则：

| 块类型 | 是否进 `text` |
|---|---|
| `text` | **是**，按出现顺序拼接 |
| `reasoning` | **否**（思考过程走 `timeline` 拉取，见 §6.2） |
| `image` / 其它 | **否**（设备无法显示，且体积不可控） |

`text` 是**本轮最后一条** assistant 消息的文本块拼接结果，不是全部轮次累加。
若本轮是工具调用后继续跑，取最终收尾那条。

#### 5.7.2 `truncated` 与长度控制

用户裁决是"会话完成必须推送结果"，但回复正文可能远超单条消息上限（§1.4 的
`maxMessageBytes` 通常几千字节，而长回复可达数万字节）。

**规则**：

| 情况 | 行为 |
|---|---|
| `text` 未超 `maxMessageBytes` | `parts = 1`，`truncated = 0` |
| `text` 超 `maxMessageBytes` | **截断到 `maxMessageBytes`**，`text` 保留**开头**部分，`truncated = 1` |

> **为什么不拆成多 part 送全文**：`maxMessageBytes` 本身就是
> `min(设备声明 maxPayload, 16 × chunkPayload, 8160)`（§1.4）——也就是
> **拆分信封能装下的上限**。也就是说，当一条消息的 `text` 超过 `maxMessageBytes`
> 时，它已经**无法**用 `part/parts` 拆分了（拆也装不下）。
> 一个 5 万字的回复需要跨越上千个消息号，且设备端根本没有足够内存缓冲整段正文。
> **截断 + `truncated=1` 让设备知道"还有更多，去电脑看"**，
> 这与思考过程"按需拉取、不用回溯"的取舍一致。
>
> **注意与 `session.input` 的区别**：`session.input` 的 `text` 超限时**由设备拆分**
> （§5.1.2 的双向规则），因为那方向没有"截断"这个选项——截断会静默丢掉用户说的话，
> 违反 C1。两个方向对超限的处理刻意不同：
>
> | 消息 | 方向 | 超 `maxMessageBytes` 时 |
> |---|---|---|
> | `session.result` | 主机 → 设备 | **截断** + `truncated=1`（长回复本来就是"去电脑看全文"） |
> | `session.input` | 设备 → 主机 | **不截断**，走 `part/parts` 分片（用户的话不能丢） |

**设备应如何呈现 `truncated = 1`**：属于设备决定（N1）。建议至少有一个"未完"标识，
让用户知道要去电脑上看全文。

#### 5.7.3 与 `session.state` 的 `done` 的关系

两者都在本轮结束时出现，但职责不同，**都必须实现**：

| 消息 | 作用 | 时机 |
|---|---|---|
| `session.state` 的 `state = "done"` | 状态指示灯转绿 | 本轮结束瞬间，受 500ms 节流 |
| `session.result` | 推送回复正文 | 本轮结束瞬间，**不受节流**（一次性事件） |

`session.result` 是**一次性事件**，不重发。若设备在收到时正忙（比如正在录音），
主机不保证补发 —— 设备可在之后拉 `timeline` 或重新看 `session.state`。
若要查看结果，设备应自己缓存收到的 `text`。

**同一 `turnId` 只推一次**。主机侧按 `(sessionId, turnId)` 去重，
避免 `turn/end` 事件重复触发导致设备看到两条。

**不落盘**：`session.result` 是**纯推送**，主机侧只做「已推送过的 `(sessionId, turnId)`」这个内存去重集合，**不把结果写任何文件**。主机重启后不补发、不会话结束前也查不回来。

**断链时的 `session.result`**：若推送时链路已断，该条丢弃不补发（与所有推送族一致）。
设备重连后拿到的 `session.state` 里该会话已是 `done` 或 `idle`，
回复正文不会自动补 — 这是推送族的固有限制，已在需求文档 §7.1 记录为体验损失。

### 6.2 timeline

拉某会话**最近 N 条**思考过程与工具调用（合成一条时间线）。

```json
{ "type": "timeline.req", "sessionId": "s_8f2a", "count": 20 }
```

| 字段 | 说明 |
|---|---|
| `sessionId` | 目标会话 |
| `count` | 要最近的多少条。主机裁剪到自己的环形缓冲上限（**默认 20**，见下方保留策略） |

```json
{
  "type": "timeline",
  "sessionId": "s_8f2a",
  "entries": [
    { "seq": 412, "kind": "reasoning", "text": "先看协议层是否已经有分片实现……" },
    { "seq": 413, "kind": "tool", "name": "bash", "field": "command", "value": "npm test" },
    { "seq": 414, "kind": "reasoning", "text": "8 条测试失败，都是 vendor 缺失……" }
  ],
  "dropped": 0,
  "hasMore": true
}
```

| 字段 | 说明 |
|---|---|
| `entries[]` | 按 `seq` 升序 |
| `entries[].seq` | 会话内单调递增序号，用于设备去重与续拉 |
| `entries[].kind` | `reasoning` 或 `tool` |
| `entries[].text` | `kind = reasoning` 时必有，思考原文 |
| `entries[].name` / `field` / `value` | `kind = tool` 时必有，工具名 + 一个关键字段（同 5.2.1 映射） |
| `dropped` | 因为**单条自身就装不下**（超过 `maxMessageBytes` 上限）而被主机整条丢弃的条数（0 表示未裁剪） |
| `hasMore` | **本次返回之外，缓冲里是否还有更旧的条目**。含义见下方说明 |

**`hasMore` 的确切含义**：它回答的是"这次是不是被 `count` 截断了"，
不是在说"能不能继续往前翻"。因为缓冲本身只有最近 20 条（§6.2 保留策略），
设 `count = 5` 且缓冲有 20 条时 `hasMore = true` —— 表示"再要 5 条还有"。
设 `count = 20`（或更大）时 `hasMore` 恒为 `false`，因为缓冲就这么大。

> **与"不用回溯"的关系**：用户裁决是"不用把历史存到磁盘、用户可以在电脑上看"。
> `hasMore` 不是回溯开关，它只是让设备知道"这次要少了"。**没有持久化，
> 主机重启或会话结束即丢** —— 设备任何时候 `count = 20` 都拿到全部可得的。

**保留策略**：

- 每个会话一个内存环形缓冲，默认保留最近 **20** 条（可配置）
  - 20 条足够覆盖"刚才它在干什么"的判断场景；设备要回溯更多应回电脑上看
  - 主机侧收到第 21 条时丢弃最旧的一条
- **不落盘、不跨重启、不做归档、会话结束即丢**
- 设备要更旧的条目 → 不可能，主机已丢弃。`hasMore` 只表示"这次没给全"，用更大的 `count` 可以再拉

**裁剪规则**：`timeline` 与其它会超限的消息一样走 §5.1.2 的拆分信封
（`ver` / `part` / `parts`），所以「20 条装不进一条消息」**不是**裁剪理由 ——
那是拆分要解决的问题。剩下唯一该裁剪的情形是：**某一条自身**的 JSON 已经超过
`maxMessageBytes` 上限（主机侧恒等于 8160 字节），无论怎么拆单个 part 都装不下，
此时主机把该条**整条丢弃**并计入 `dropped`。条目一律不得截断内容（C1）。

设备侧组装 `timeline` 时按 `part` 升序把各片的 `entries[]` **依次拼接**，
`dropped` 取各片之和（主机保证每片的值相同，取任一片亦可）。

## 7. ASR 族

**ASR 是一个无状态、无副作用的纯服务**：音频进，文本出。它不关心文本要用到哪里。

这个边界很关键：设备可能把结果填进提问的自定义答案、用于审批回复、显示在屏幕上、或者干脆丢掉——全部是设备自己的事，主机不参与。

### 7.1 asr.begin / 音频 / asr.end（设备 → 主机）

```json
{ "type": "asr.begin", "requestId": 3, "codec": "ima-adpcm", "sampleRate": 16000, "channels": 1 }
```

| 字段 | 说明 |
|---|---|
| `requestId` | 0..15，本次转写的句柄。同一时刻只允许一个在途 |
| `codec` | **只有 `ima-adpcm`**（4:1 压缩）。原因见 §7.1.2「为什么没有 `pcm16`」 |
| `sampleRate` | 16000（默认）或 8000 |
| `channels` | 固定 1 |

**`asr.begin` 本身没有应答**（不存在 `asr.started`）。设备的成功信号是
「主机没有在收到 `asr.begin` 后立即回 `asr.error`」——它可以开始推音频。

**但主机在无法转写时必须立即回 `asr.error`，不要等 `asr.end`。** 典型情形：
语音服务未就绪、没有可用 provider、已有一个 `requestId` 在途。设备收到
`asr.error` 就停止录音并释放资源；若主机拖到 `asr.end` 才报错，设备已经
白录满 30 秒（236 KB 上行流量 + 用户白说）。

```json
{ "type": "asr.error", "requestId": 3, "code": "ASR_NOT_READY", "message": "语音识别服务未就绪" }
```

立即回错的判定发生在收到 `asr.begin` 的**同一帧处理内**，因此实际时序是：
设备发 `asr.begin` → 主机立刻回 `asr.error` → 设备停下。若设备在主机的
`asr.error` 到达前已经推了几帧音频，主机按 `requestId` 找不到活动 session
静默丢弃即可（`AUDIO` 通道不重组，无从报错）。

随后设备在 `AUDIO` 通道连续发送原始字节：

- 帧头 `msgId` = `requestId`
- 帧头 `frag` = 流序号（4 位回绕），仅用于断档诊断
- 每帧 ≤ `chunkPayload` 字节
- **不做重组、不去重、按到达顺序追加**

```json
{ "type": "asr.end", "requestId": 3 }
```

音频总时长上限 30 秒（`ASR_MAX_SECONDS`）。超时设备应自行停止。

**数据量（实测基准见 §7.1.2）**：

| 编码 | 30 秒字节数 | 速率 | 占实测带宽 15–17 KB/s |
|---|---|---|---|
| `ima-adpcm` | 241 908 B ≈ **236 KB** | 7.87 KB/s | 46%–52% |
| `pcm16` | 960 000 B ≈ **938 KB** | 31.25 KB/s | 184%–208%（**传不完**） |

### 7.1.1 IMA ADPCM 块格式（强制）

**设备必须按此格式分块，主机按此格式解码。这是唯一约定，不允许"实现自己发挥"**——
块边界错一个字节，解码出来的就是噪音，而且不会有任何错误码。

**块 = 4 字节块头 + 504 字节数据 = 508 字节。**

| 偏移 | 长度 | 内容 |
|---|---|---|
| 0 | 2 | `predictor`：该块第一个样本的预测值，**int16 小端有符号** |
| 2 | 1 | `stepIndex`：该块起点的 STEP 表下标，**uint8，范围 0..88** |
| 3 | 1 | 保留，填 `0` |
| 4 | 504 | 压缩数据，**每字节 2 个 4 位样本，低 nibble 在前** |

**关键规则**：

1. **每块 504 字节数据 = 1008 个样本 = 63.0 ms** @ 16000 Hz。
   因此 30 秒录音 = **476 个满块 + 1 个尾块（4 字节头 + 96 字节数据）**。
2. **状态跨块保持**：`predictor` 与 `stepIndex` 是**滚动状态**，每个块头里存的是
   "解码这一块之前的状态"。设备在块头写入当前状态后，用同一状态解/推这一块，
   块尾的状态又成为下一块的头。**不是每块重置。**
3. **低 nibble 先**：一个字节里 `低 4 位` 是时间上更早的那个样本。
   高 nibble 先的实现会得到完全错乱但"听起来像说话"的噪音。
4. **尾块**：最后一个块的数据部分不足 504 字节时，只发实际字节数，
   主机按 `ceil(剩余样本 / 2)` 字节解码。**块头 4 字节不能省。**
5. **没有"整除"这种判断**。合法码流本来就**几乎不可能**被 508 整除——
   设 total = 508k（刚好 k 个完整块），则 `(total - 4) % 508 = 504 ≠ 0`，
   所以按"是否整除"做判断会把**每一段结构完全正确的录音**都判成畸形。
   主机只做一件事：**按块头游标往前读**（见下方伪码）。

6. **块头不完整就停**：剩余字节 `< 4`（装不下一个块头）时停止解码，
   这些字节**没有意义**，直接丢弃、不报错。这是"尽力而为"的边界。

7. **尾块可以只有块头没有数据**：`remaining - 4 = 0` 时该块贡献 0 个样本，
   忽略即可（有的编码器收尾会多写一个空头）。

**解码循环（主机侧，唯一正确写法）**：

```
off = 0
while (total - off) >= 4:              # 够一个块头才进
    dataLen = min(504, total - off - 4)  # 尾块可能不足 504
    decodeBlock(buf, off, dataLen)       # 头 4 字节 + dataLen 字节数据
    off += 4 + dataLen
# 循环结束：若 total - off > 0，说明剩下 1..3 字节不足块头，丢弃
```

对 30 秒满录音（total = 241908）走一遍：476 个满块 + 1 个 96 字节尾块
= 477 块 = 480000 个样本 = **正好 30.000 秒**，剩余 0 字节。

**参考实现（解码侧）**：

```js
const IMA_INDEX_TABLE = [-1,-1,-1,-1,2,4,6,8,-1,-1,-1,-1,2,4,6,8];
const IMA_STEP_TABLE = [
  7,8,9,10,11,12,13,14,16,17,19,21,23,25,28,31,34,37,41,45,50,55,60,66,
  73,80,88,97,107,118,130,143,157,173,190,209,230,253,279,307,337,371,
  408,449,494,544,598,658,724,796,876,963,1060,1166,1282,1411,1552,1707,
  1878,2066,2272,2499,2749,3024,3327,3660,4026,4428,4871,5358,5894,6484,
  7132,7845,8630,9493,10442,11487,12635,13899,15289,16818,18500,20350,
  22385,24623,27086,29794,32767,
];

function decodeBlock(buf, offset, dataLen, out) {
  let predictor = buf.readInt16LE(offset);
  let stepIndex = Math.min(88, buf[offset + 2]);
  // 只读该块声明的 dataLen 字节，不要用 buf.length 兜底（那是上一个 bug 的来源）
  const end = offset + 4 + Math.min(dataLen, 504);
  for (let i = offset + 4; i < end; i++) {
    const byte = buf[i];
    for (const nibble of [byte & 0x0f, (byte >> 4) & 0x0f]) {
      const step = IMA_STEP_TABLE[stepIndex];
      let diff = step >> 3;
      if (nibble & 1) diff += step >> 2;
      if (nibble & 2) diff += step >> 1;
      if (nibble & 4) diff += step;
      predictor += nibble & 8 ? -diff : diff;
      predictor = Math.max(-32768, Math.min(32767, predictor));
      stepIndex = Math.max(0, Math.min(88, stepIndex + IMA_INDEX_TABLE[nibble]));
      out.push(predictor);
    }
  }
  return { predictor, stepIndex };  // 下一块的头 = 这里的返回值
}

/** 整个音频流的唯一入口。返回 Int16 样本数组。 */
function decodeAdpcm(buf) {
  const out = [];
  let off = 0;
  while (buf.length - off >= 4) {
    const dataLen = Math.min(504, buf.length - off - 4);
    decodeBlock(buf, off, dataLen, out);
    off += 4 + dataLen;
  }
  // buf.length - off > 0 时剩下 1..3 字节不足块头，丢弃
  return out;
}
```

> 注意 `nibble & 8` 是符号位：置位表示向负方向。`step >> 3` 是基础增量，
> 三位分别加 `>>2` / `>>1` / 全量。这是 IMA ADPCM 的标准算法，
> v1 的 `lib/bridge/voice.js` 里有一份已验证的实现可作交叉参考。

### 7.1.2 为什么没有 `pcm16`（实测吞吐约束）

用户实测 BLE 有效吞吐 **约 15–17 KB/s**。据此：

| 场景 | 结论 |
|---|---|
| `pcm16` 录 30 秒 | 需 938 KB。按 15 KB/s 要 **62 秒**才能传完，而录音只有 30 秒——**必然积压，链路被音频独占，且永远传不完** |
| `pcm16` 在 30 秒窗口内能传多少 | 15 KB/s × 30 s = 450 KB ≈ **14 秒**的音频。要么掉音频，要么超时 |
| `ima-adpcm` 录 30 秒 | 236 KB，7.87 KB/s，占用带宽 **46%–52%**，剩一半给控制通道（`session.state`/审批/提问） |

所以 **`codec` 只有 `ima-adpcm` 一个合法值**。设备若发 `codec: "pcm16"`，
主机回 `asr.error{code:"ASR_FAILED", message:"不支持的 codec: pcm16"}`，
不要静默降级（降级会得到一个"听起来正常但内容是错的"结果，比明确失败更糟）。

**同理，`sampleRate` 的 8000 Hz 也只是备用档**：8 kHz ADPCM 只有 3.94 KB/s，
但识别质量明显下降。默认必须用 16000。

### 7.1.3 音频帧切分与块边界**无关**

音频帧（`AUDIO` 通道上的每一帧，≤ `chunkPayload` 字节）与 ADPCM 块（508 字节）
是**两个独立的层次**：

- **ADPCM 块**是编码器的概念，主机解码时按 508 字节边界对齐
- **音频帧**是传输层的概念，只是为了塞进 ATT MTU

一帧可以跨越两个块，一个块也可以被劈成三帧。**帧边界不参与解码**——
主机把所有 `AUDIO` 帧的 payload 按到达顺序拼成一个连续字节流，再按 508 字节
切块解码。所以：

- 设备**不需要**在块边界处强制分帧
- 设备**不需要**补齐块尾（尾块本来就不满）
- 设备**不要**在帧里加任何块标记

按 MTU 分档的实际帧数（30 秒满录音，241 908 字节）：

| MTU | chunkPayload | 帧数 |
|---|---|---|
| 517 | 510 | 475 |
| 247 | 240 | 1 008 |
| 244 | 237 | 1 021 |
| 23 | 16 | 15 120 |

> 最后一档（MTU 23）在 15 KB/s 下需要约 16 秒传完 236 KB，
> 仍然在 30 秒窗口内，但剩余带宽只剩 6%，控制通道会明显卡顿。
> **设备应主动请求 MTU 247 或更大。**

### 7.1a asr.cancel（设备 → 主机）

用户在录音过程中按了取消，或设备检测到自己误触时使用。

```json
{ "type": "asr.cancel", "requestId": 3 }
```

| 字段 | 说明 |
|---|---|
| `requestId` | 要取消的转写句柄 |

**主机行为**：

1. 若该 `requestId` 有在途 session → 丢弃已累积的全部音频字节，释放缓冲
2. **不回任何消息**（既不发 `asr.result` 也不发 `asr.error`）。取消是设备主动发起
   的，结果对它没有意义；主机若再回一条，设备还得为"已取消的请求"维护状态
3. 若 `requestId` 不存在或已结束 → 静默忽略

**与 `asr.error` 的关系**：绝不用 `asr.error` 表达"已取消"。两者的区别是
**谁发起**：`asr.error` 由主机发起（转写失败），`asr.cancel` 由设备发起（用户放弃）。
若主机因取消而回 `asr.error{ASR_CANCELLED}`，设备会看到一个自己从未触发过的错误码，
徒增分支。

**释放后 `requestId` 可立即复用**：同一 `requestId` 下一次 `asr.begin` 是全新的 session，
不继承任何旧状态。

**`asr.cancel` 之后到达的音频帧**：设备应停止发送；若仍有在途帧到达主机，
主机按其 `msgId` 找不到活动 session → 静默丢弃（`AUDIO` 通道不重组，无从报错）。

### 7.2 asr.result（主机 → 设备）

```json
{ "type": "asr.result", "requestId": 3, "text": "用 macOS 构建", "durationMs": 2400 }
```

| 字段 | 说明 |
|---|---|
| `text` | 识别文本，**不截断**。超 `maxPayload` 时按 `part/parts` 拆分 |

### 7.3 asr.error（主机 → 设备）

```json
{ "type": "asr.error", "requestId": 3, "code": "ASR_NO_PROVIDER", "message": "未配置语音识别服务" }
```

| `code` | 含义 |
|---|---|
| `ASR_NO_PROVIDER` | 宿主没有可用的语音识别服务 |
| `ASR_NOT_READY` | 服务存在但模型未就绪 |
| `ASR_TIMEOUT` | 转写超时（60 秒） |

### 7.4 ASR 不做什么

| 不做 | 说明 |
|---|---|
| 不绑定会话 | 没有 `sessionId` 参数 |
| 不自动注入 | 主机不会把文本写进任何会话 |
| 不保留历史 | 转写完即丢，`requestId` 不跨请求复用语义 |
| 不做确认往返 | 没有"待确认"状态 |
| 不认领、不降级 | 没有 `voice.pending` / `take` / `ack` / 2.5 秒降级直发 |

> **由于音频只回给发起请求的设备，"对着护照说话、字落进电脑输入框"这个旧体验不会自动存在。** 如果将来要保留，需要设备显式发一个新的控制动作，由主机执行。当前不做。

## 8. 控制族

### 8.1 session.cancel

设备请求停止一个会话（AI 偏离意图时的处置）。

```json
{ "type": "session.cancel", "sessionId": "s_8f2a", "reqId": "c_17" }
```
```json
{ "type": "session.cancel.ack", "reqId": "c_17", "ok": true }
```

失败时：

```json
{ "type": "session.cancel.ack", "reqId": "c_17", "ok": false, "code": "CANCEL_NOT_RUNNING", "message": "该会话当前没有在执行" }
```

| `code` | 含义 |
|---|---|
| `CANCEL_NOT_FOUND` | 会话不存在或已结束 |
| `CANCEL_NOT_RUNNING` | 会话存在但不在运行，无需停止 |
| `CANCEL_FAILED` | 宿主拒绝或内部错误 |

**延迟要求**：无特殊要求。走普通请求-应答，链路忙时可排队几百毫秒。

### 8.1a session.input（设备 → 主机）

设备**主动发起**，向**已有会话**追加一条用户消息。等价于用户在电脑键盘上打一句话发出去。

```json
{ "type": "session.input", "sessionId": "s_8f2a", "text": "用 pnpm 而不是 npm", "reqId": "i_21" }
```
```json
{ "type": "session.input.ack", "reqId": "i_21", "ok": true }
```

失败时：

```json
{ "type": "session.input.ack", "reqId": "i_21", "ok": false, "code": "INPUT_NO_SUCH_SESSION", "message": "会话不存在" }
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `sessionId` | string | **必填，无默认值**。目标会话必须由设备显式指定 |
| `text` | string | 用户消息正文，**不截断**。超 `maxPayload` 时按 §5.1.2 由**设备**拆分，主机收齐后回 ack |
| `reqId` | string | 本次请求 ID，用于 `ack` 配对。**所有分片共用同一个 `reqId`** |

| `code` | 含义 | 设备应如何提示 |
|---|---|---|
| `INPUT_NO_SUCH_SESSION` | `sessionId` 不存在（可能已被删除） | "会话不存在，请先刷新列表" |
| `INPUT_EMPTY_TEXT` | `text` 为空串 | 不应发生；设备侧应先阻止空提交 |
| `INPUT_REJECTED` | 宿主拒绝（会话正在被其它操作占用等） | 直接显示 `message` |
| `INPUT_FAILED` | 内部错误 | 显示 `message`，可重试 |

#### 8.1a.1 三条关键语义（**实现必须遵守**）

**① `sessionId` 必填，主机绝不猜。**
这是约束 C2（主机不得替设备决定内容去向）在协议上的直接体现。不存在"默认当前会话"、
不存在"最近活动的会话"这种回退 —— v1 的 `#resolveTargetSession` 猜会话正是要删掉的东西。
设备从 `session.state` 或 `session.list` 拿到 `sessionId`，自己决定发给谁。

**② 会话结束后**仍可**继续**。**
DSH 的会话是持久化的。一个会话处于 `done` 或 `idle` 状态时收到 `session.input`，
主机照常投递，DSH 会**开新一轮**继续跑。设备不需要"先唤醒会话"。

因此 `session.input.ack.ok = true` 只表示"消息已投递进会话"，
**不表示**"响应已经产生"。响应通过两条路径回来：

- `session.state` 里该会话的 `state` 变回 `running`（推送，500ms 节流）
- 本轮结束时收到 `session.result`（见 §5.7）

**③ 只做"追加用户消息"，不做其它写操作。**
不新建会话、不切换模型、不改工作目录、不发文件。设备侧能做的写操作就这一条，
配合已有的"停"（`session.cancel`）构成完整闭环：**看 + 停 + 说 + 续**。

#### 8.1a.2 会话 ID 从哪来

设备必须自己持有 `sessionId`。两个来源：

| 来源 | 时机 |
|---|---|
| `session.state` 推送 | 主机主动推，`sessions[].id` |
| `session.list` 拉取 | 设备刚上电/唤醒或想刷新时主动拉 |

`session.input` 的 `ack` **不回传**新的会话列表 —— 设备若担心会话已过期，
应在收到 `INPUT_NO_SUCH_SESSION` 后重新拉 `session.list`，再让用户重选。

### 8.2 approval.decide

```json
{ "type": "approval.decide", "id": "ap_7k2n_1", "decision": "allow" }
```

`decision` ∈ `allow` / `deny`。主机会回 `approval.done` 通知最终结果。

**设备与电脑端同时呈现，谁先答谁算数。** 设备提交后若发现电脑端已抢先裁决，
收到的 `approval.done` 里 `decidedBy` 会是 `pc`，设备据此收起卡片即可。

### 8.3 question.answer

```json
{
  "type": "question.answer",
  "callId": "q_9m4x",
  "action": "submit",
  "answers": [
    { "id": "q1", "selected": ["macOS"], "custom": null }
  ]
}
```

| 字段 | 说明 |
|---|---|
| `action` | `submit` / `cancel` / `reject` |
| `answers[].id` | 题目 ID |
| `answers[].selected` | 选中的选项 label 数组（单选也放在数组里） |
| `answers[].custom` | 自定义输入文本（通常来自 ASR），无则 null |

`action = cancel` 表示用户放弃作答；`reject` 表示用户明确拒绝回答该问题。

**两个 action 落到 DSH 的映射**（DSH 的提问结果只有三态，必须明确对应）：

| 设备 `action` | 主机行为 | DSH 看到的结果 |
|---|---|---|
| `submit` | 组装 answers 交给 DSH | 正常返回答案 |
| `cancel` | 不投递任何答案，让 DSH 的提问以"取消/超时"结束 | `ASK_TIMED_OUT` 或等效取消 |
| `reject` | 同上，但**额外**记录一次"用户明确拒绝" | 同 `cancel` |

> **`cancel` 与 `reject` 对 DSH 效果相同**，区别只在于主机侧日志与面板显示的措辞。
> 这是 DSH 侧能力所限（提问没有独立的"拒绝"结局），不为它造假的第四态。
> 设备若想表达"拒绝"，可以在 UI 上区分，但协议上两者等价于同一结局。

## 9. 保活与断链

### 9.1 保活（v2 重新设计）

旧实现有三个缺陷：① `missedHeartbeats` 在发 ping **之前**自增，跳过发送时也计数；② 注释说"收到任何控制消息都算存活"，但只有 `pong` 会清零；③ 发送队列积压时仍发 ping，加剧拥塞。

v2 规则：

```
lastInboundAt = 收到任意通道任意帧的时间戳
每 5 秒检查一次：
  if (now - lastInboundAt >= 5000)  → 发 ping
  if (now - lastInboundAt >= 30000) → 判定断链，主动 disconnect
```

- **阈值一律用「大于等于」`>=`，不要用严格 `>`**。检查周期恰好也是 5 秒，所以检查时刻永远精确落在阈值上（5000、10000、…）；写成 `>` 会让第一个 ping 整整推迟一个周期（空闲 10 秒才发）、判死推迟到 35 秒，既与「空闲满 5 秒就发 ping」的字面意思不符，也让 30 秒判死变成 35 秒。设备侧实现同样用 `>=`。
- **任何入站帧都刷新 `lastInboundAt`**（不只是 `pong`），因为对端在发任何东西都证明它活着
- 有业务流量时不发 ping（省带宽）
- `HEARTBEAT_MISS_LIMIT` 由"6 次 × 5 秒"变为"连续 30 秒无入站"，语义更清晰

**设备侧必须实现对等规则**（协议是双向的，不能只约束主机）：

```
设备侧同样维护 lastInboundAt = 收到任意通道任意帧的时间戳
每 5 秒检查一次：
  if (now - lastInboundAt >= 5000)  → 发 ping
  if (now - lastInboundAt >= 30000) → 判定断链，主动断开并开始重连退避
```

| 规则 | 主机 | 设备 |
|---|---|---|
| 任意入站帧刷新存活 | 必须 | **必须** |
| 空闲 5 秒后主动发 `ping` | 必须 | **必须** |
| 连续 30 秒无入站判死 | 必须 | **必须** |
| 判死后动作 | `transport.disconnect()`，按退避重连 | 主动断开 GATT，按退避重扫重连 |
| 对 `ping` 的应答 | 回 `pong` | **必须回 `pong`** |
| 退避序列 | 1/2/5/10/20/30 秒 | 建议同主机（非强制，设备可自行决定） |

> **为什么设备侧也必须发 ping**：主机侧 `session.cancel`、`approval.asked` 等下行
> 消息在链路异常时会静默失败。若只有主机发 ping，设备无法察觉"主机已经不再听我
> 说话"，会一直停在某个界面等下去。双向保活才能让两端各自独立发现断链。

**`ping` 的载荷**：`{"type":"ping","seq":N}`，`pong` 原样回 `seq`。`seq` 仅用于
调试对照，接收方不做校验（不匹配也正常刷新存活时间）。

### 9.2 断链处理

链路断开时主机必须清理所有"等设备响应"的状态，否则 DSH 那一轮对话永久悬挂：

| 域 | 清理动作 |
|---|---|
| 审批 | 所有 pending 结算为 `cancelled`，发 `approval.done`，清空设备待审批状态 |
| 提问 | 所有 pending 结算为 `cancelled`，发 `question.done` |
| ASR | 在途请求回 `asr.error{ASR_FAILED}` 或直接丢弃（链路已断，发不出去） |
| 发送队列 | 全部 reject，防止 await 永挂 |

> 旧实现只有提问域做了断链清理，审批域完全没有（`approval.timeoutMs` 默认 0 不超时）——断链后 DSH 对话永久悬挂。这是必须在 v2 修掉的缺陷。

### 9.3 重连

- 意外断开按 `[1, 2, 5, 10, 20, 30]` 秒退避重连
- 主动断开不重连
- 重连后**必须重新握手**，不沿用旧 `maxPayload`、不沿用旧会话状态

  - 主机取 `min(双方)`，若低于自己支持的最低版本 → 回 `hello.ack` 后立即断开，并报 `PROTO_MISMATCH`
  - **不再"只打一条 warn 就当没事"**（旧实现的实际行为）
- v2 **不兼容 v1**。旧固件连上新主机：收到的消息类型全部不认识 → 回 `nack{UNKNOWN_TYPE}`，最终表现为"连上但什么都不动"。这是**预期行为**，不是 bug。

### 11.1 向后兼容的预留

- `flags` bit 3、能力位 7..15、CTRL 特征保留字节：连上后一律填 0，接收方忽略未知位
- 所有 JSON 消息：接收方**忽略未知字段**（保证小步加字段不需要改版本号）
- 新增消息类型时不改 `PROTOCOL_VERSION`（`hello.proto` 只在大改时递增）

## 12. 帧示例

一条 `session.state`（2 个会话，约 300 字节），MTU 247（`chunkPayload = 240`），
因此拆成 2 片。取 `msgId = 165 = 0x0A5`：

```
帧 0: [0x25][0x00][0x0A][0x50]   FIRST|ACK_REQ, CONTROL, msgId=0x0A5, frag=0
帧 1: [0x26][0x00][0x0A][0x51]   LAST |ACK_REQ, CONTROL, msgId=0x0A5, frag=1
```

逐字节推演（**以实现为准，不要凭直觉填**）：

| 字节 | 帧 0 | 帧 1 | 计算 |
|---|---|---|---|
| 0 高半字节 | `0x2` | `0x2` | `version = 2` |
| 0 低半字节 | `0x5` | `0x6` | `FIRST(0x1)｜ACK_REQ(0x4)` / `LAST(0x2)｜ACK_REQ(0x4)` |
| 1 | `0x00` | `0x00` | `channel = CONTROL = 0` |
| 2 | `0x0A` | `0x0A` | `msgId >> 4` |
| 3 高半字节 | `0x5` | `0x5` | `msgId & 0x0F` |
| 3 低半字节 | `0x0` | `0x1` | `frag` |

设备重组完成后回 `ack`（复用同号 `msgId`，单帧）：

```
[0x20][0x00][0x0A][0x50]   flags=0, CONTROL, msgId=0x0A5, frag=0
```

> **`ack` / `nack` / `ping` / `pong` 的 flags 规则**：这四条链路层消息
> **一律置 `flags = 0`**，不带 `ACK_REQ`（否则无限递归），也不用 `FIRST/LAST`
> 表达完整性 —— 接收方按"单帧即完整"处理。业务消息仍必须正确置位。

## 13. 已定案项

以下各项原为待裁定，现已由用户拍板，实现时不再讨论：

| # | 问题 | 结论 | 说明 |
|---|---|---|---|
| 1 | 每个会话保留的时间线条数 | **20 条** | "没必要这么多，20条不少了" |
| 2 | bash 命令原文可能含密钥，链路不加密 | **照发原文，不脱敏** | "照发" |
| 3 | 会话集合是否带模型名、工作目录 | **带** | "带吧"——新增 `model`、`cwd` 两个可选字段 |
| 4 | `session.state` 推送频率上限 | **最小间隔 500ms** | "500ms 1条吧"——超出的变化合并为延迟推送 |
| 5 | 设备在线时是否抑制电脑端审批卡片 | **不抑制** | "不要抑制，可以正常审批。审批完通知终端即可。" / "谁抢到是谁的" |
| 6 | 桌面挂件是否保留 | **保留，仿照现有形式** | "可以仿照现在的形式" |
| 7 | 设备能否向会话写内容 | **可以，向已有会话追加一条用户消息**（`session.input`） | "设备主动发起，向已有会话新增" |
| 8 | 会话结束后能否继续 | **可以**，投递即开新一轮 | "可以" |
| 9 | `session.input.sessionId` 是否必填 | **必填，主机绝不猜** | "是的" |
| 10 | 会话完成时是否推送结果 | **必须推送**（`session.result`），超限截断并置 `truncated=1` | "另外会话完成也必须推送结果给设别" |

**第 5 项的完整规则（双端竞速）**：

审批在电脑端和设备端**同时呈现**，两端都能裁决，**先到先算**。

| 事件 | 主机动作 |
|---|---|
| 电脑端先裁决 | 结算 outcome，发 `approval.done{decidedBy:"pc"}` → 设备收起卡片 |
| 设备先裁决 | 结算 outcome，abort 电脑卡片，发 `approval.done{decidedBy:"device"}` |
| 设备迟到裁决（已结算） | 忽略，设备会从 `approval.done` 得知已被 `pc` 处理 |
| 断链 | 结算 `cancelled`，电脑卡片仍在，用户可在电脑上正常完成 |

**为什么不抑制电脑卡片**：设备可能在手边也可能不在，电脑前的人也可能正盯着屏幕。
任何抑制都会让"另一端的人"以为卡片丢了。同时呈现 + done 通知是唯一不会
让人误判的方案。

**"审批完通知终端"的具体含义**：`approval.done` 是**唯一**的审批终态通知，
所有结局（设备裁决、电脑裁决、超时、中止、断链）都发这一条，设备收到即收起卡片。

> `ASR_MIN_SAMPLES = 8000` 即 0.5 秒 @ 16000 Hz。时长下限用**采样数**判定，
> 不用浮点秒数，避免浮点比较和不同采样率下的歧义。

> 30 秒满录音 = `floor(480000 / 1008) = 476` 个满块 + 1 个尾块 = **241 908 字节**。
>
> `BLE_MIN/MAX_THROUGHPUT_BPS` 是**实测参考值**（用户实测 15–17 KB/s），
> 不是协议协商值——协议里没有吞吐协商，它只用来判断"某种 codec 是否可行"。
