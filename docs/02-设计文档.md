## 1. 设计目标

| # | 目标 | 对应需求 |
|---|---|---|
| 1 | 协议是独立可交付的契约，不是代码的副产品 | C1–C4、G5 |
| 2 | 传输层可脱离真实 BLE 完整测试 | NFR-8 |
| 3 | 业务能力彼此独立，任一失效不拖累其余 | C9 |
| 4 | 状态的生命周期任何一处都不能悬挂 | C5 |
| 5 | 主机侧零呈现决策，零屏幕尺寸常量 | C1–C3 |
| 6 | 加一个业务能力只需加一个文件 | 可演进 |

## 2. 分层

```
┌──────────────────────────────────────────────────────────┐
│ 宿主接口层（DSH 服务 + 事件 + 工具 + 面板 + 挂件）        │
│  host/          approval · questions · sessions · tools   │
├──────────────────────────────────────────────────────────┤
│ 能力层（协议服务端对外的四类能力）                        │
│  api/           push · pull · asr · control               │
├──────────────────────────────────────────────────────────┤
│ 链路层（谁连上了、握手完没完、消息怎么发出去）            │
│  link/          link · handshake · pairing · keepalive     │
├──────────────────────────────────────────────────────────┤
│ 传输层（字节怎么变成消息，与业务无关）                    │
│  wire/          constants · frame · reassembler · acks     │
│                 · msgid · codec                            │
├──────────────────────────────────────────────────────────┤
│ 传输驱动（进程边界）                                      │
│  ble/           transport · bridge-client · bridge-worker  │
└──────────────────────────────────────────────────────────┘
```

**依赖方向严格单向向上**：下层不知道上层存在。`wire/` 不 import `link/`，
`link/` 不 import `api/`，`api/` 不 import `host/`。唯一的反向通道是
事件回调（下层 emit，上层 on），不直接调用。

## 4. 模块设计

### 4.1 wire/ · 传输层

**职责**：把 `Uint8Array` 变成 `{channel, msgId, type, payload}`，以及反向。

| 模块 | 关键接口 | 说明 |
|---|---|---|
| `constants.js` | 常量全集 | 与协议文档 §3 逐条对应 |
| `frame.js` | `encode(msgId, channel, bytes, maxChunk) → frames[]`<br>`decodeHeader(bytes) → {version, flags, channel, msgId, frag}` | 纯函数，无状态 |
| `reassembler.js` | `push(channel, bytes) → {kind:'message'\|'gap'\|'stale'\|'overflow', …}` | 无定时器、无 IO |
| `acks.js` | `track(msgId, frames, onGiveUp)`<br>`acknowledge(msgId)` | 自带退避序列 |
| `msgid.js` | `allocate() → id`<br>`release(id)` | 环形扫描 |

**设计要点**

- `frame.js` 与 `reassembler.js` **不共享状态**，可以被同一组测试用例对撞
  （encode 后 decode 应还原）。
- `reassembler` 的 key 是 `${channel}:${msgId}`，音频通道（channel=1）
  **不进入 reassembler**，这是 C6 的结构性保证：`link.js` 在分派前就分流。
- `acks` 的重传序列暴露为可注入参数（`retryDelays = [400,800,1600]`），
  测试可直接断言重传时刻。

### 4.2 ble/ · 传输驱动

**职责**：让"发送一串字节"和"收到一串字节"变得和网络 socket 一样普通。

| 模块 | 关键接口 |
|---|---|
| `transport.js` | `start() / stop() / send(bytes) / state / mtuPayload`，事件 `data / state / disconnected / error` |
| `bridge-client.js` | 与 `bridge-worker.js` 的 JSONL 协议（`{id, cmd}` / `{id, ok, value}` / `{event,…}`） |
| `bridge-worker.js` | noble 扫描、设备识别、连接、特征发现、MTU 协商、写入、通知 |
| `mock-transport.js` | 内存实现，注入 `{dropRate, latencyMs, mtuPayload, failConnect}` |

**设计要点**

- `transport.js` 的钩子是 `doStartScan / doStopScan / doConnect / doDisconnect /
  doSend / doDispose`（下划线约定，不是 `#private`）。理由：`#` 私有方法
  词法绑定，子类同名方法不会覆盖，钩子会静默失效——v1 实测踩过。
- 错误分两件事：`classifyError()` 定类别（权威）、`humanizeError()` 定文案
  （可重推）。`toUserError = humanize( classify(x) )` 是唯一出口。
- `bridge-worker.js` 完全不知道自己服务的是 AI Passport 还是别的什么协议，
  它只知道"这个 UUID 特征要 write，那个要 subscribe"。

**`data` 事件的 `channel` 元数据契约**（M2 实现时补全）

`data(bytes, meta)` 的 `meta.channel` 是**字符串**，取值集合固定为四个：

| `meta.channel` | 对应的帧头数值通道 | 含义 |
|---|---|---|
| `'control'` | `CHANNEL_CONTROL`(0) | 控制通道，JSON 业务消息 |
| `'audio'` | `CHANNEL_AUDIO`(1) | 音频上行（ASR 录音） |
| `'heartbeat'` | `CHANNEL_HEARTBEAT`(2) | 保活 ping/pong |
| `'log'` | `CHANNEL_LOG`(3) | 设备日志（仅诊断） |

**`meta.channel` 必须反映帧头的真实通道，不能按发送方向或调用点硬编码。**
传输层不解析 JSON、也不该替上层判断"这条大概是什么"，它唯一的职责是把
收到的字节连同来源通道原样交出去。实现要求：

- `bridge-client.js` 透传 worker 事件里的 `channel` 字段（`obj.channel ?? 'control'`）；
- `mock-transport.js` 必须按**帧头**的 `channel` 数值反查上表得到字符串，
  不能一律写 `'control'`；
- 数值通道到字符串的映射只在 `wire/constants.js` 定义一次（`CHANNEL_NAME`），
  两层共用，避免各处手写字符串。

> M2 验收踩坑：`mock-transport.js` 曾把 `meta.channel` 硬编码为 `'control'`，
> 而帧头真实通道是 2。HEARTBEAT 上的 `pong` 因此带着错误的元数据，
> 上层若按 `meta.channel` 分流就会把保活帧当业务帧。当时测试全绿——因为
> 测试自己也在 CONTROL 上发 ping，实现与测试印证了同一个错误假设。

### 4.3 link/ · 链路层

**职责**：维护"一条可用链路"，并在链路变化时通知上层。

```js
class Link extends EventEmitter {
  // 状态
  get state()          // idle|scanning|connecting|connected|reconnecting|failed
  get ready()          // 握手完成
  get info()           // {deviceId, name, firmware, maxPayload, maxChunks, capabilities, paired}

  // 生命周期
  async start()
  async stop(reason)
  async restartScan(reason)

  // 收发
  async send(type, payload, {ack=true, channel=0} = {})
  async sendAudio(bytes, requestId)      // 不重组、不确认、不重传
}
```

**设计要点**

- 握手由**设备**发起（`hello`），主机回 `hello.ack` 并给出最终
  `maxPayload`/`maxChunks`。这是 v2 的定案，与 v1 的注释相反——v1 的
  常量注释把方向写反了。
- **保活改为"任意入站帧刷新 `lastInboundAt`"**（C7）。v1 只在 pong 时归零，
  语音上行期音频挤占控制通道会导致误判断链。
- 断链时 `Link` 广播一次 `disconnected`，**各能力层自己清理自己的 pending**
  （C5）。`Link` 不持有业务状态，所以它不能替上层清理，但必须保证事件一定发出。
- `sendAudio()` 与 `send()` 走不同路径：前者直接切分发送、不分配消息号、
  不登记 ACK。

### 4.4 api/ · 能力层

每个能力是一个类，构造签名统一：

```js
new Capability({ link, log, host })
// host = { sessions, approvals, questions, asr, balance }  // 宿主侧能力注入
```

| 模块 | 负责消息 | 断链清理 |
|---|---|---|
| `push.js` | `session.state` / `session.result` / `approval.asked` / `approval.done` / `question.asked` / `question.done` / `notice` | 重推一次全量快照；清空节流计时器；`session.result` **不受 500ms 节流**（一次性事件） |
| `pull.js` | `session.list.req` / `timeline.req` / `balance.req` | 丢弃在途应答 |
| `asr.js` | `asr.begin` / `asr.end` / `asr.cancel` | **丢弃所有在途录音**（C5）；`asr.cancel` 不回执（见协议 §7.1a） |
| `control.js` | `session.cancel` / `session.input` / `approval.decide` / `question.answer` | 通知被取消的对象；`session.input` 投递到宿主并回 ack |

**设计要点**

- `server.js` 是一张 `type → handler` 表，未命中回 `unknown_type` 错误
  （v1 是静默 emit `unhandled`，无监听者，等于黑洞）。
- `push.js` **不知道**设备怎么显示，它只负责"把主机的状态说清楚"。
  截断、分页、排序都在设备侧。
- `pull.js` 的时间线条目**整条保留**（C1）。装不下时整条丢弃并如实报告
  `dropped`，不做字段级裁剪。
- `asr.js` 是**无状态服务**：`asr.begin` 起一个 session，音频追加，
  `asr.end` 转写并回文本，然后忘掉一切。没有 `target`、没有注入、没有过期。
- **音频只在 `asr.begin` 之后累积**：`codec` 只有 `ima-adpcm` 一个合法值
  （协议 §7.1.2 有实测带宽论证），收到其他值立即回 `asr.error{ASR_FAILED}`，
  **不静默降级**。`api/asr.js` 只在 `asr.end` 时解码，`AUDIO` 帧按到达顺序
  拼成连续字节流，再按 508 字节（4 头 + 504 数据）切块交给 IMA 解码器——
  **帧边界与块边界无关**（协议 §7.1.3）。块状态（`predictor`/`stepIndex`）
  跨块滚动，不能每块重置。

### 4.5 host/ · 宿主接口层

| 模块 | 职责 | 关键不变量 |
|---|---|---|
| `attach.js` | 接 DSH 服务、订阅事件、串联各域 | 全程 try/catch，失败不影响宿主 |
| `approvals.js` | 拦截 `approval/request`，双端竞速 | 必须有断链清理 |
| `questions.js` | 拦截 `user-questions/request` | 同上 |
| `sessions.js` | 维护会话集合与主从关系 | `role` 必须显式判定；带 `model`/`cwd` |
| `timeline.js` | 环形缓冲 + 工具关键字段映射 | 整条存整条发 |
| `tools.js` | 4 个 Agent 工具 | 声明 `output:{schema,render}` |
| `panel.js` | Web 面板 | 写方法必须回环 |
| `state.js` | 对外快照 | 只读视图，不持有业务状态 |
| `widget.js` | 桌面挂件（预构建 bundle） | 四个区固定：链路胶囊 / 设备信息 / 配对码 / ASR 状态 |

**设计要点**

- `approvals.js` / `questions.js` **呈现策略一致**：都是"双端同时呈现、先答者胜、
  落败方由 done 消息收起"。但两者**仍不共用同一个类**：审批是一次性裁决
  （entry 落定即删、允许粒度只有一次），提问是整批作答 + 途中导航
  （`question.nav` / `question.pick` 只是 UI 交互，不结算）。合并会得到一个
  两个用例都不舒服的抽象。共用的是 `#race()` 与 `#settle()` 两个辅助函数。
- `widget.js` 的形态按 D28 **仿照 v1 现有形式**，不再自行设计：

  | 区域 | 内容 | 与 v1 的差异 |
  |---|---|---|
  | 链路胶囊 | 状态点 + 状态文字 + 关注角标 | 角标数字改为按会话集合统计 `attention` 数 |
  | 设备信息 | 固件 / 电量 / 信号 / 握手 + 断开、诊断按钮 | 不变 |
  | 配对码 | 6 位数字输入框 + 提交 | 不变 |
  | ASR 状态 | 服务是否可用 + 「准备模型」按钮 | **不做** v1 的"识别结果填草稿"交互 |

  v1 挂件里已被用户要求删除的**审批区、余额区、任务区**在 v2 中**不恢复**——
  审批在设备上做，余额由设备自己拉，任务状态已被会话集合取代。
- `sessions.js` 判断主从：DSH 事件带 `parentSessionId`（子会话有，主会话无）。
  **role 由这个字段显式决定**，不靠计数推测。
- `timeline.js` 的工具关键字段映射是**一张数据表**，不是 if 链：

  ```js
  const TOOL_FIELD = {
    bash: 'command',
    write: 'path', edit: 'path', read: 'path',
    glob: 'pattern', grep: 'pattern',
  };
  ```
  查不到就只发工具名。**永不 fallback 到"发全部参数"**。
- `attach.js` 的装配顺序必须是：心跳日志 → 配置 → logger → 注册 disposer →
  面板注入行（最早）→ 创建 runtime → `inject(['webServer','sessionController'])`
  → `inject(['tools'])` → 异步 autoConnect。

## 5. 关键数据流

### 5.1 会话状态推送

```
DSH session/event
      │
      ▼
host/sessions.js  更新 running 集合、runStarts、title、parentId
      │  emit('changed')
      ▼
api/push.js       计算全量快照 {ver, part, parts, sessions[]}
      │           ① 内容签名去重（同签名不重发）
      │           ② 500ms 节流：距上次推送不足 500ms 则合并为一次延迟推送
      │              （只保留最后一次状态，不排队堆积）
      ▼
link.send('session.state', snapshot)   ack=true
      │
      ▼
wire/frame → ble/transport → 设备
```

**为什么推全量而不是增量**：设备是无状态客户端，重连后必须能立刻重建视图；
增量需要设备维护版本协商与丢失恢复，复杂度远高于收益。载荷量：10 个会话
含 `title`/`model`/`cwd` 约 1.6KB，单条消息内（NFR-2）。

**为什么是 500ms 节流而不是不限频**（D26）：主会话 + 3 个子代理同时跑时，
`elapsedMs` 每秒各变一次、标题与状态也各自变，不限频会出现每秒十余条推送，
把链路预算吃掉。500ms 合并后最坏 2 条/秒，且合并取的是**最后一次状态**，
不会丢失最终态；节流实现用「尾沿触发」——定时器只在有变更且静默期满时发一次。

**节流不得吞掉关键跃迁**：`attention` 从 `none` 变为 `approval`/`question`
时**立即推送，绕过节流**。理由是弹提醒的时效性直接影响用户能否及时处置，
而 500ms 的节流窗口对"会话状态显示"无感，对"弹提醒"有感。

### 5.2 审批竞速

**用户裁决（D27）：不抑制电脑卡片，正常审批，审批完通知终端；"谁抢到是谁的"。**

```
DSH approval/request
      │
      ▼
host/approvals.js  ① 立刻启动电脑分支 promise(电脑卡片) —— 无条件，不等设备
                   ② 若设备在线且可处理：发 approval.asked，等设备
                   ③ Promise.race([电脑, 设备])
                      电脑先答 → 结算 outcome，发 approval.done{decidedBy:'pc'}
                                让设备收起卡片
                      设备先答 → 结算 outcome，abort 电脑卡片
                                发 approval.done{decidedBy:'device'}
      │
      ▼
返回 ApprovalOutcome 给 DSH
```

`deviceEligible` 的判定（决定要不要**通知设备**，不影响电脑卡片）：

| 条件 | 来源 |
|---|---|
| 链路 `connected` 且握手 `ready` | `link.ready` |
| 设备 `paired = 1` | `hello` 报的能力 |
| 该工具在设备可裁决范围内 | 配置 `approval.deviceToolScope`，见下方 §5.2.1 |

#### 5.2.1 `approval.deviceToolScope`（原 `readOnlyToolsOnDevice`）

旧名 `readOnlyToolsOnDevice: false` 的语义是"只读工具**也**交给设备"，
双重否定让所有人读反。改名并改成显式枚举：

| 取值 | 含义 |
|---|---|
| `"all"`（默认） | 所有工具都通知设备，由设备决定要不要呈现 |
| `"write-only"` | 只有写类工具（`risk = high`）通知设备；只读工具直接在电脑上处理 |
| `"none"` | 一律不通知设备，审批完全在电脑端 |

> **为什么不保留布尔**：布尔无法表达"只通知写操作"这个中间态，而这个中间态
> 是最可能被用到的（只读工具审批太频繁，设备一直弹提醒很烦）。枚举一次说清。
>
> **`risk` 与作用域的关系**：协议里的 `risk` 字段（`low` / `high`）由主机按工具是否
> 只读算出，与作用域**无关** —— 作用域决定"发不发"，`risk` 只描述"发了之后告诉设备什么"。

#### 5.2.2 `paired` 的来源（原表述不准）

上一版写"设备 `paired = 1` 来源是 hello 报的能力"，这是错的。实际来源：

| 环节 | 谁判断 |
|---|---|
| 设备 `hello{token}` 带 token | 设备提供凭证 |
| 主机查本地信任表 `~/.dsh/dsh-ai-passport.pairing.json` | **主机**校验，比对 `deviceId` + `token` |
| 主机在 `hello.ack.paired` 里告知结果 | 主机回执 |

设备侧只是**记住**上次握手收到的 `paired`，并不自己判断是否已配对。

**关键约束**：

1. **电脑分支无条件启动**。这是 v1 的真实事故：v1 曾在"设备在线"时不启动
   电脑分支，导致电脑端永远看不到卡片。现在任何情况下卡片都出现。
2. **落败方必须收到 done**。设备先答 → `approval.done{decidedBy:'device'}`
   让电脑卡片收起；电脑先答 → `approval.done{decidedBy:'pc'}` 让设备收起。
   这就是用户说的"审批完通知终端"。
3. **断链 → 结算 `cancelled`**（C5）。此时电脑分支仍在跑，用户可在电脑上正常完成。
4. **设备不合格 → 只走电脑分支**，不发 `approval.asked`，也就不会有 done 要发给设备。
5. **迟到裁决忽略**。"谁抢到是谁的"意味着竞速一旦落定，另一端后来的 `approval.decide`
   不再生效（`#settle` 幂等：`if (entry.settled) return false`）。设备靠收到的
   `approval.done.decidedBy` 得知自己输了，而不是靠主机再回一条拒绝。

**为什么审批不能"总是允许"**：DSH 的 `ApprovalOutcome` 只有
`allowed-once` / `rejected` / `cancelled` / `unavailable`，且
`grants apply only to the requested action`。设备若提供"总是允许"按钮，
主机只能落到 `allowed-once` 并记 warn，不为它造假的持久授权。

### 5.3 时间线拉取

```
设备 timeline.req {sessionId, count}
      │
      ▼
api/pull.js  从 host/sessions 取该会话环形缓冲的最后 count 条
      │      按 seq 升序
      ▼
组装 entries[] → 估算字节 → 超上限则从最旧开始整条丢弃
      │
      ▼
回 timeline {sessionId, entries, dropped, hasMore}
```

**字节预算**：先按 `maxPayload` 试装，装不下就减条目，直到装下或为空。
`dropped` 如实告知丢了几条，设备据此决定是否再拉。

### 5.4 ASR

```
设备 asr.begin {requestId, codec, rate, channels}
      │
      ▼
api/asr.js  建 session，**不回执**（无法转写时立即回 asr.error）
      │
设备 AUDIO 通道持续发帧（不重组、不确认）
      │
      ▼
api/asr.js  追加字节，检查超限（30s）
      │
设备 asr.end {requestId}
      │
      ▼
拼 WAV → speech.transcribe() → asr.result {requestId, text, durationMs}
       失败 → asr.error {requestId, code, message}

设备 asr.cancel {requestId}（任意时刻）
      │
      ▼
api/asr.js  丢弃已累积字节、释放缓冲、**不回任何消息**
            （取消是设备发起的，结果对它无意义；见协议 §7.1a）
```

### 5.5 会话续接（session.input）

```
设备 session.input {sessionId, text, reqId}
      │
      ▼
api/control.js
      ├── sessionId 不存在            → ack{ok:false, code:"INPUT_NO_SUCH_SESSION"}
      ├── text 为空串                 → ack{ok:false, code:"INPUT_EMPTY_TEXT"}
      └── 会话存在
            │
            ▼
      host/sessions.js 投递：
        sessionController.prompt({ sessionId, mode:'queue',
                                   content:[{type:'text', text}] })
            │
            ▼
      ack{ok:true}            ← 只表示"已投递"，不表示"响应已产生"
            │
            ▼
      该会话 state 变回 running → session.state 推送（受 500ms 节流）
            │
            ▼
      本轮结束 → session.result 推送（不受节流）
```

**三条实现约束**：

1. **`sessionId` 必填且不猜**。`control.js` 里不得出现任何"没有 sessionId 就取最近的
   / running 的 / 最新的"回退逻辑。v1 的 `#resolveTargetSession` 正是这么写的，必须删掉。
   查不到就回 `INPUT_NO_SUCH_SESSION`，让设备重新拉 `session.list`。
2. **`done` / `idle` 状态照常接受**。不检查 `state` 就投递，DSH 自己会开新一轮。
   唯一需要拒绝的是会话已从宿主消失（`sessionController.list()` 查不到该 id）。
3. **投递失败不重试**。`ack.ok = false` 就是最终答复，主机不在内部重试。
   设备若想重试，自己再发一次（`reqId` 会不同，不影响幂等判断）。

### 5.6 会话完成推结果（session.result）

```
DSH session/event {type: "turn/end", ...}
      │
      ▼
host/sessions.js  取本轮最后的 assistant 消息正文
      │              （content 里 type === "text" 的块按序拼接）
      ▼
api/push.js
      ├── 按 (sessionId, turnId) 去重 —— 同一轮只推一次
      ├── elapsedMs 起点不可靠 → 整字段省略
      └── text 超 maxMessageBytes → 截断并置 truncated = 1
      │
      ▼
link.send('session.result', payload)     ← 不受 500ms 节流
```

**为什么 `session.result` 与 `session.state` 的 `done` 是两条消息**：

| | `session.state` 的 `done` | `session.result` |
|---|---|---|
| 载荷 | 会话集合全量快照（只多了一个 `state` 值） | 本轮回复正文 |
| 频率 | 受 500ms 尾沿合并节流 | **不受节流**，一次性 |
| 语义 | "指示灯该变绿了" | "这是它说了什么" |
| 去重 | 按内容签名 | 按 `(sessionId, turnId)` |

合并不划算：`session.state` 是全量快照，把回复正文塞进去会让每 500ms 的快照都背着
几 KB 文本；而且 `state` 会在 8 秒后转 `idle` 再推一次，回复正文会被重复携带。

**`text` 的取法**（与协议 §5.7.1 对应）：

```js
// 取本轮最后一条 assistant 消息里的 text 块
const last = events[events.length - 1];
const text = last.data.message.content
  .filter((b) => b.type === 'text')
  .map((b) => b.text)
  .join('');
// reasoning / image / 其它块一律不进 result
```

**不落盘**：`push.js` 只维护一个 `sentResults: Set<`${sessionId}:${turnId}`>` 的内存集合用于去重，
**不写任何文件**。主机重启后集合清空、不补发历史结果。这与时间线环形缓冲的取舍一致（N6/N6b）。

**断链时丢弃不补发**：与全部推送族一致。设备重连后靠 `session.state` 得知该会话
已完成，但拿不到正文 —— 这是推送族的固有限制，已在需求文档 §7.1 记录为体验损失。

## 6. 状态生命周期与清理矩阵

C5 的核心：**每一个"等设备"的状态都必须有一个"链路没了"的清理路径**。

| 状态持有者 | 断链时必须做的事 | 忘了会怎样 |
|---|---|---|
| `link/handshake` | 重置 `ready=false`，丢弃 `info` 中的动态部分 | 重连后误判已就绪 |
| `wire/acks` | 清空待确认表（不重传旧消息） | 重连后疯狂重传历史消息 |
| `wire/msgid` | 释放所有在途号 | 号段泄漏，最终耗尽 |
| `api/control` 的 `session.input` | 无需清理（无状态，投递完就结束） | — |
| `api/push` 的 `sentResults` | **不清**（跨连接保留，防止重连后重推同一 turn） | 重连后重复推送同一轮结果 |
| `link` 发送队列 | 全部 reject，防止 await 永挂 | 上层 await 悬挂 |
| `host/approvals` | 所有 pending 结算为 `cancelled` | DSH 对话永久悬挂（v1 真实缺陷） |
| `host/questions` | 同上 | 同上 |
| `api/asr` | 丢弃在途录音，回 `asr.error`（若还发得出去） | 内存泄漏 + 下次录音串字节 |
| `host/sessions` | 保留 `runStarts`（计时不归零），清 `deviceRecording` 类抑制标志 | 时长少算（v1 缺陷） |
| `api/push` | 重连后强制重推全量快照 | 设备停在旧状态 |

测试要求：对每一行都写一个"断链后 X 已被清理"的用例（见 §8）。

## 7. 协议事实源的单一化

v1 的 `test/protocol-parity.test.js` 用正则解析固件 `app_proto.h` 再和 JS 常量对撞。
它现在 8 条全红，因为 `vendor/ai-passport` 从未 clone。这个设计有两个问题：
跨仓库依赖让测试必然脆弱；正则解析 C 头文件本身就是脆的。

v2 方案：**协议文档 §3 的常量表是权威，机器可读副本在本仓库内**。

```
docs/03-蓝牙协议规格.md   ← 人读，权威
        │  手工同步（改协议必须同时改两处）
        ▼
src/wire/constants.js     ← 机器可读
        │
        ▼
test/wire/constants.test.js  ← 校验 JS 常量与文档表格逐项一致
```

具体做法：测试读取 `docs/03-蓝牙协议规格.md`，解析其中的常量表格
（严格固定格式，如 `| `PROTOCOL_VERSION` | 2 | uint8 |`），与
`src/wire/constants.js` 的导出逐项比对。

这样：
- 不需要跨仓库，CI 永远可跑。
- 文档与代码不同步会**立刻红灯**——这比"解析别人的 C 头文件"更可靠。
- 固件仓库自己维护 `app_proto.h`，并以本仓库文档为准。

## 12. 风险

| # | 风险 | 影响 | 应对 |
|---|---|---|---|
| R1 | 协议变更需要固件同步重烧 | 两端不同步则完全不通 | 协议先冻结（本文档 + 03），固件按 §3 常量表实现；版本不符即拒绝并给明确错误 |

| R3 | 会话状态全量推送在多会话并发时频繁 | 占用链路带宽 | 内容签名去重；必要时设备可改拉取模式 |

| R5 | 工具关键字段可能含敏感信息（bash 命令里的密钥） | 未加密链路泄露 | **已定案：照发原文不脱敏**（D24）。安全边界依赖应用层配对（认领信任），不做链路加密 |
| R6 | DSH 宿主 API 变化（`approval/request`、`user-questions/request` 形状） | 插件失效 | 事件形状兜底 + 单测用假宿主锁定契约 |
